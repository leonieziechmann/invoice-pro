######## loom-capabilities

SUMMARY:
loom 0.1.1 is a pure recursive content walker (no state/context). `weave` builds `ctx = (sys:..) + inputs`, runs `max-passes - 1` measure passes plus one draw pass; each pass applies `injector(ctx, previous-payload)`. invoice-pro uses max-passes 2: pass 1 sees empty `global`, the draw pass sees root's pass-1 signal (total, formated-total, bank); scope+measure run twice, draw once; no convergence check ever runs. Per component: scope(ctx) -> traverse AND DRAW children -> measure(ctx, child frames) -> draw(ctx, public, view, body). So data goes down only via scope/ctx, up only via frames, and a parent's draw can only wrap finished child content. Motif kinds: plain, managed (path + auto frame), compute, data (leaf), content (draw-only `(ctx, body)`). Today `ctx.theme` is a flat dict of render functions called as `(ctx.theme.slot)(ctx, view)`; `theme()` is evaluated before weave without arguments.

Enablers (all verified by prototypes in proto/loom-capabilities): ctx inheritance yields a real, sibling-isolated cascade; a 5-line deep-merging scope motif (`mutator.merge-deep("theme", overrides)`) gives partial subtree overrides, including swapping one render slot in a real invoice; one wrapper motif can drive both the ctx cascade (scope) and Typst's set-rule cascade (draw); function-valued lazy derived tokens work; `derive` is the existing auto=inherit idiom; footer/header content woven with `eval-content` reads totals (`ctx.global`) in the draw pass; `eval-content` also works inside `layout`/`context`; labels on draw output are valid show-rule hooks.

Limits: the shipped `apply` (loom's and invoice-pro's) is shallow and wipes all other theme slots; `ensure`/`ensure-deep` treat explicit `none` as missing (use defaults<-user merge-deep instead); `nest` wipes non-dict values; no layout info can enter loom data (`context` in measure is opaque content) so page-aware features must live inside render functions; motifs inside `context`, `layout`, or named fields (figure caption, page header) silently vanish unless woven via eval-content, and their signals are lost; labelled containers in the body crash the engine ("unexpected argument: label"); motifs with a different loom key (key is versioned `<invoice-pro:0.4.2>`) are silently ignored, which matters for third-party themes; nesting budget is ~19 extra wrapper levels in a real invoice; with max-passes 2 second-order dependencies on `global` are stale by one generation; compile cost scales with ctx size x closure calls (~20 ns per dict entry per call; content/bytes are cheap), current ctx is 275 leaves so a few hundred tokens are negligible, but large collections in ctx or per-node re-application of default trees are expensive, and one nested `theme` key beats flat top-level keys. loom bugs: `observer` typo (broken), `assert-root` always fails, `update` skips patch-only keys, `matcher.display` not exported (invoice-pro carries a copy).

Matcher: `match(value, pattern, strict:)` returns only bool; patterns are types, literals, tuples, records (all keys required, extras allowed unless strict) plus descriptors any/choice/many/dict/exact/instance; switch/case normalises shorthands (returns none when nothing matches). Through `types.require` a failing nested dict prints the whole value and whole schema with no failing path; a 12-line path-tracking walker produces "token `theme.font.size` ("10pt") must be of length", supports partial dicts and unknown-key detection. Side finding: base-theme's header/footer `set page` rules sit inside `if` blocks and have no effect (only DIN-5008's footer path works).

TOP FINDINGS:

1. ctx inheritance gives a real CSS-like cascade for free: a scope override affects only its subtree and is isolated from siblings (verified t1), so scoped theme overrides are natively supported by loom.
2. The shipped apply() (loom's and invoice-pro's own at src/loom-wrapper.typ:18-22) is a SHALLOW top-level replace: apply(theme: (...)) wipes every other theme slot in the subtree (verified t7); the theming API needs a deep-merging scope motif, which is 5 lines using loom.mutator.merge-deep (verified in a real invoice, swapping just the signature slot).
3. Lifecycle order is scope -> children measured AND drawn -> parent measure -> parent draw: theme data must be in ctx at scope time; a slot function only receives finished body content and can wrap/style it (Typst set/show rules cascade into child output) but cannot re-parameterise children; one wrapper motif can drive both the ctx cascade and the Typst style cascade (verified t12).
4. Apply token defaults as 'defaults <- preset <- user' via merge-deep, not ensure/ensure-deep: those treat an explicit none as missing and overwrite it with the default (verified t3); also merge-deep always deep-merges dict-valued tokens (no wholesale replace) and nest() wipes any non-dictionary ctx.theme.
5. loom.matcher.match returns only a bool, requires every record key (no optional keys, partial theme dicts fail), lets unknown keys pass unless strict, and via types.require prints the whole value plus whole schema with no failing path; a small path-tracking per-leaf walker reusing match/display yields messages like: token `theme.font.size` ("10pt") must be of length (verified t2b/t2c).
6. Data flowing up is available to themes only in the draw pass via ctx.global (root publishes total, formated-total, bank; theme.document and eval-content'ed header/footer additionally get items, item-data, payment-goal); verified a page footer printing total due. With max-passes 2, anything that feeds aggregated data back into signals is stale by one generation, so theme logic must be presentation-only.
7. No layout information can enter loom's data flow (context inside measure yields opaque content); page-aware features (carry-over subtotals, first-page variants, continued markers) must be implemented inside render functions with Typst context/state, which draw functions are allowed to return.
8. Motifs placed inside context blocks, layout(), or named content fields (figure caption, page header/footer) are silently dropped; slots that host user content must weave it with eval-content (works even inside layout/context, verified t9), and signals from such content are lost.
9. Labelled container elements in the woven body crash loom 0.1.1 ('unexpected argument: label', engine.typ:193/218), so user-side labels on containers cannot be styling hooks; labels emitted by draw output work fine with show rules.
10. Performance scales with ctx size times closure calls (~20 ns per dict entry per call due to Typst argument hashing; content/bytes values are cheap): today's ctx has 275 leaves so hundreds of tokens cost milliseconds, but keep theme under ONE nested key, resolve defaults once rather than per component, and never inject large collections into ctx (loom's default injector made an 1600-node weave 10x slower).
11. The loom key is versioned (<invoice-pro:0.4.2>, bumped each release) and motifs with another key are silently ignored (verified t10): third-party themes should be pure data plus plain functions, not motif-emitting code tied to a package version; nesting budget is about 19 extra wrapper motif levels inside a real invoice before Typst's call-depth limit.
12. loom 0.1.1 defects to avoid or fix upstream: weave(observer:) is broken by a typo (runtime.typ:117), guards.assert-root always fails, mutator.update skips keys that exist only in the patch, matcher.display is not exported (invoice-pro keeps a copy); side finding: base-theme header/footer set-page rules are scoped inside if-blocks and have no effect (src/themes/base-theme/base.typ:35-40).

1. Can loom be patched/released alongside invoice-pro v0.5.0 (same author)? Fixing the label crash, exporting matcher.display, adding an optional()/path-reporting matcher and a deep apply would remove several workarounds from the theming design.

3. Should dict-valued tokens (inset, margin, stroke dicts) deep-merge on override or be replaced wholesale? loom's merge-deep offers only deep merge.
4. Which additional document-level facts (item count, has-discounts, tax breakdown, currency, payment-goal) should root publish into ctx.global so body-level theme slots can react to them, and is raising max-passes to 3 acceptable if any of them become second-order dependencies?
5. Is the versioned loom key intended to stay? It determines whether third-party theme packages may emit invoice-pro motifs (dynamic, etc.) or must be restricted to data + plain functions.
6. Should theme() keep being evaluated before weave with no arguments, or should theme resolution move into root's scope so presets can depend on locale/sender/ctx (cost: runs once per pass)?

######## api-philosophy

SUMMARY:
The report distils 19 design principles (each with path:line evidence), a complete reference of the `locale.custom` patch DSL, the end-to-end locale customization flow, 17 inconsistencies/defects not to copy, and a clearly marked inference section with a compiled feasibility sketch.

Core philosophy: every configurable thing is a LAZY FUNCTION the engine calls late with context, passed UNCALLED by the user and customized with Typst's native `.with(...)`: locale = `(..overrides, base-lang, base-region) => dict` (src/locale/factory.typ:37-38, called at src/invoice.typ:181), unit = `(locale) => dict`, reference sign = `(label:, value:) => ctx => (title, val)`, country = `(name:, code:, show-always:) => dict`. Customization is "master schema + cascading strict patches": base-language -> lang -> user strings-patches, then base-region -> region(final-lang) -> user region-patches, folded by a depth-2 merge meant to panic on unknown keys; the result is re-shaped into a flat "Normalized" consumer dict (strings, format, normalize, currency, tax, meta, resolve-plural). The running package injects the base schema, giving third-party locales forward compatibility (docs locale/custom.md:14). Two tiers are documented: tweak via `.with(locale.custom.*)`, author via `locale.build-locale(lang, region)` for publishable packages.

`locale.custom` has one helper per schema group (11 language helpers emitting `(strings: (<group>: payload))`, 3 region helpers emitting `(region: (...))`), all params default `auto`, `_clean-auto` strips `auto` so `none` remains a real value. SUMMARY:
Scope: prior art for theming APIs (Typst ecosystem + web/LaTeX) and hard Typst constraints, each verified by compiling prototypes with typst 0.15.1 under scratchpad/proto/prior-art/ (c01..c13). Repo untouched. Side effect: the cetz test made typst download @preview/oxifmt:1.0.0 into the global package cache. Nothing was run on 0.14.0 (declared min compiler).

Status quo: theme = zero-arg function returning a slot dict (document/header/footer/line-items/bank-details/payment-goal/signature), stored in loom ctx, consumed in component draw passes. DIN-5008 exposes only 8 knobs; the generic line-items renderer already has ~25 flat style params + ~15 render-_ hooks with auto=default and exported default-render-_ ("super"). Four hard-coded look variants exist unexported.

Ecosystem: touying = namespaced config fragments (config-colors/store/methods) merged recursively into a `self` object, user args last, value-or-function slots; cetz = style tree with `auto` inheritance to nearest ancestor and stroke-dict folding (ran its real resolver on an invoice-shaped tree successfully); fletcher = diagram-level defaults for auto element options; tidy = style is a module/dict of render functions + separate colors dict (same architecture as invoice-pro); elembic = pure-Typst custom elements with `#show: e.set_()` but ~30-rule nesting limit, context opacity, dependency risk -> reject; valkyrie -> reject, reuse in-house base-pull merge/types.require; brilliant-cv = user-loaded metadata.toml with string lengths and preset-or-hex colors; no Typst letter/invoice package has real theming (ceiling: font, one accent, banner, margins). Cross-ecosystem: DTCG tiers primitive->semantic->component with {alias}; CSS custom properties + named @layer precedence; Tailwind extend vs replace; MUI seed color -> derived light/dark/contrastText, components.{defaultProps,styleOverrides,variants}; Chakra slot recipes/variants; Docusaurus wrap-vs-eject with safe/unsafe slot stability classes; KOMA-Script scrlttr2 separates pseudo-lengths (geometry), options (toggles), variables (content+labels), element fonts (style), bundled in stackable .lco profiles (DIN, SN, NF, UScommercial9, Nippon) - the closest domain prior art.

Verified constraints: no set/show on user functions; set/show rules in the theme document wrapper reach components, address block and page header/footer but only as defaults - explicit component args (header-color: black, table strokes/fills) win, and wrapper table rules bleed into user tables; user rules inside the body override, rules before the template lose to theme rules; label hooks (`show <ip-line-items>: ...`) work through loom and do not break page-breaking; deep merge costs ~0.05-0.1 ms for 300 leaves (closure calls are memoized); functions in dicts/.with()/wrap-with-super work, no reflection; WCAG contrast and OKLCH palette derivation work exactly in pure Typst; toml/json/yaml fine, no length constructor (eval works but is not file-sandboxed; a regex parser works), packages cannot open user path strings (pass dict/bytes/content, or path() on 0.15+ only); PDF images work but fail under --pdf-standard a-3b (ZUGFeRD) - SVG works; letter-pro owns set page(background/footer) so a letterhead background is silently discarded; page x/y, state, counters work in wrapper-level set page; apply(theme: ..) scoped override works but replaces ctx.theme wholesale.

Bugs found: base-theme header/footer slots are dead code (set page inside `if {}` block, base.typ:35-40); motifs inside `context` are invisible to loom (dynamic() renders empty in a contextual footer).

Catalogue (16 mechanisms) recommends: tiered token dict with aliases/lazy derivation (core), seed-derived accessible palette, slot renderers with wrap/super + stability tiers, variants as data, a separate .lco-like geometry profile (requires owning the page frame instead of letter-pro), a locale.custom-style patch DSL as primary surface, brand-file loader as a token patch, deep-merging scoped override motif, label hooks and minimal native set-rule layer as escape hatches, page furniture (letterhead/header/footer/page-number) as first-class slots; reject elembic and valkyrie; cetz-style implicit inheritance only partially (auto=inherit, none=off, fold partial strokes).

TOP FINDINGS:

1. Typst 0.14/0.15 has no user-defined elements or set/show rules for custom functions (verified); all theming must travel as data/functions through loom ctx or piggy-back on built-in elements and labels - elembic emulates it but with ~30-rule nesting limits, context opacity to loom and dependency risk, so it should be rejected for v0.5.
2. Native set/show rules in the theme's document(ctx, body) wrapper reach component output, the address block and page header/footer, but only as defaults: every explicit arg the components pass (header-color: black at components/line-items/line-items.typ:44, explicit table strokes/fills) wins, and wrapper-level table rules also restyle user tables in the body (verified).
3. User set rules placed inside the body override theme set rules for body/component content, while rules placed before '#show: invoice' lose against anything the theme sets (e.g. font at DIN-5008/document.typ:80) - so themes should set as little as possible natively and expose tokens instead (verified).
4. A tiered token dictionary (primitive -> semantic -> component) with '{alias}' strings and lazy 't => value' leaves, resolved once after a recursive deep merge, is fully feasible and cheap (~0.05-0.1 ms per merge of 300 leaves; patching only the brand seed re-derived stripe, header fill and auto-contrast text in the prototype).
5. WCAG contrast ratio, on-color selection, ensure-contrast loops and OKLCH tonal ramps from ONE seed color work exactly in pure Typst via color.linear-rgb().components() (asserted 21.0 / 4.48 / 4.54 reference values); lighten()-based ramps are visibly worse than OKLCH ramps.
6. Slot renderers with access to the default renderer ('wrap, don't eject' a la Docusaurus) work via closures, and label hooks ('show <ip-line-items>: it => ...') work through loom without breaking multi-page tables; the real v0.5 contract is therefore the shape of ctx/data passed to slots, which needs stable-vs-internal classification.
7. KOMA-Script's .lco model (pseudo-lengths for address window, fold marks, ref line, first-page footer; separate options, variables and element fonts; stackable profiles for DIN/SN/NF/US/Nippon) is the closest domain prior art and argues for a geometry profile axis separate from style; today geometry is locked in letter-pro's hard-coded numbers.
8. letter-pro's letter-generic owns set page(background:, footer:), so a letterhead background set by theme or user is silently discarded under the DIN theme (verified); invoice-pro must own the page frame (~120 lines) to support letterheads, custom marks and non-DIN layouts.
9. PDF letterheads are incompatible with ZUGFeRD: image('x.pdf') fails under --pdf-standard a-3b with 'embedding PDFs is currently not supported in this export mode' while SVG letterheads and transparency compile fine under a-3b (verified on 0.15.1).
10. Brand files: toml/json/yaml load fine but a package cannot open a user path given as string (resolved inside the package dir); the user must pass the parsed dict, bytes or content, or a path() value which exists only in typst 0.15+; there is no length constructor, eval works but can read files/import on 0.15.1, a 10-line regex parser is the safer option; files cannot express auto, so absence must mean inherit.
11. Status-quo bugs found: base-theme's header/footer slots never apply because 'set page' sits inside an 'if { }' block (src/themes/base-theme/base.typ:35-40), and motifs such as dynamic() inside 'context { }' are invisible to loom and render empty - header/footer slot functions should receive ctx as an argument.
12. apply(theme: (line-items: fn)) already gives scoped theme overrides through loom ctx with function values intact, but it replaces ctx.theme wholesale (loom-wrapper.typ:18-22); a deep-merging scope motif is needed, and dictionary.map/filter, path(), spot colors and page bleed are 0.15-only while typst.toml declares compiler 0.14.0.

OPEN QUESTIONS:

1. Should the minimum compiler be bumped from 0.14.0 to 0.15.0 for v0.5.0? That would unlock path() for brand/letterhead files inside the package, dictionary.map/filter, spot colors and page bleed; none of my verification ran on 0.14.0 (eval file access and the PDF/A error for PDF images may behave differently there).
2. Is the maintainer willing to drop or fork the letter-pro dependency so that invoice-pro owns the page frame (set page background/footer, address window geometry)? Without that, geometry profiles, letterhead backgrounds and non-DIN country layouts are not achievable.
3. Which parts of ctx and of the per-slot data dictionaries (line-items view, bank, payment-goal, signature) are meant to be a stable public contract for custom slot renderers, and which are internal? This determines how much of the 'wrap/eject' surface can be locked in v0.5.0.
4. How should insufficient contrast or invalid brand values be reported? Typst has no user-level warning API - only panic or visible content; a strict/lenient switch may be needed.
5. Should brand-file strings be parsed with a restricted parser (predictable, data-only) or with eval (more expressive, but executes code and can read files on 0.15.1)?
6. Does loom evaluate labelled/show-rule-transformed content correctly for all motif types? I only verified label hooks and scoped apply for the line-items component.
7. Should themes be allowed to supply default arguments for user-called components (MUI defaultProps analogue, e.g. column-order or QR code on/off), or must the theming contract stay purely presentational? Not prototyped.
8. Are the four existing look variants (elegant, vibrant, luxury, informational in src/themes/base-theme/line-items.typ) intended to become public presets? They are the best concrete test cases for a variants-as-data design.
