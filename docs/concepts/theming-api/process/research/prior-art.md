# Prior Art for a Theming API + Hard Typst Constraints

Researcher focus: prior art (Typst ecosystem + cross-ecosystem) and language constraints, verified with typst 0.15.1 (9dfd3a08).
All prototypes live in `<session>/proto/prior-art/` (abbreviated `PA/` below). Repo paths are relative to `<repo>`.

Legend: **[V]** = verified by compiling on typst 0.15.1; **[V-src]** = verified by reading real source (local package cache or fetched raw source); **[doc]** = taken from official docs/web page, not executed; **[mem]** = from memory, not re-checked. The package declares `compiler = "0.14.0"` (`typst.toml:12`); nothing here was executed on 0.14.0, 0.15-only features are flagged.

## 0. TL;DR for designers

1. Typst (0.14/0.15) has **no user-defined elements, no set/show rules for user functions** [V]. Everything "themeable" must travel as _data_ (dicts/functions) through loom's `ctx`, or piggy-back on _built-in_ elements (text, table, block, heading, label selectors).
2. Native set/show rules written in the theme's `document(ctx, body)` wrapper **do reach** everything drawn by components, the address block and even page header/footer [V] - but only as _defaults_: every explicit argument a component passes (`header-color: black`, explicit `stroke:`/`fill:` on the table) wins over them [V]. The current line-items component passes ~25 explicit style values, so set rules are a weak lever today.
3. A **token dictionary with tiers (primitive -> semantic -> component), lazily derived values and `{alias}` references** is cheap and fully feasible [V]: a recursive deep-merge of a 300-leaf/3-level dict costs ~0.05-0.1 ms; WCAG contrast and palette derivation from ONE seed color work in pure Typst [V].
4. **Slot renderers with access to the default ("super")** - Docusaurus "wrap, don't eject" - are trivially expressible with closures [V], and also via native `show <label>: it => ...` if components label their output [V].
5. **Layout geometry should be separated from style** like KOMA-Script's `.lco` files (pseudo-lengths for address window, fold marks, ref line, first-page footer). Today geometry is outsourced to `@preview/letter-pro:3.0.0`, which owns `set page(background:, footer:)` - so a theme/user **cannot add a letterhead background** (it is clobbered) [V].
6. **Letterhead as PDF is incompatible with ZUGFeRD**: `image("x.pdf")` works normally [V] but fails under `--pdf-standard a-3b` with "embedding PDFs is currently not supported in this export mode" [V]. SVG letterheads work under a-3b [V].
7. **Brand files**: `toml()/json()/yaml()` work; packages cannot open user paths given as strings [V]; user must pass the parsed dict, bytes, or (0.15 only) a `path(...)` value [V]. There is no `length("12pt")` constructor [V]; use `eval` (not sandboxed from the file system on 0.15.1 [V]) or a 10-line regex parser [V].
8. Status-quo bug found on the way: `base-theme`'s `header:`/`footer:` slots are **dead code** - `set page(...)` sits inside an `if { }` block and is scoped away (`src/themes/base-theme/base.typ:35-40`) [V]. Also, motifs inside `context { }` are invisible to loom (`dynamic(...)` renders empty in a contextual footer) [V].

## 1. Status quo snapshot (what the prior art has to be mapped onto)

- A theme is a **zero-arg function returning a dict of slot renderers**: `invoice(theme: themes.DIN-5008())` (`src/invoice.typ:21`), type-checked as `function` (`src/invoice.typ:106`), evaluated once with `theme()` (`src/invoice.typ:180`) and stored in loom ctx as `ctx.theme` (`src/invoice.typ:291`).
- `base-theme(document:, header:, footer:, line-items:, bank-details:, payment-goal:, signature:)` returns the dict (`src/themes/base-theme/base.typ:8-50`). `blank = base-theme` (`src/themes/blank/blank.typ:3`).
- `DIN-5008(form, font, hole-mark, folding-marks, color-row-odd, color-row-even, margin, footer)` returns `base-theme.with(document: letter-document(..), line-items: render-line-items.with(..))` (`src/themes/DIN-5008/din-5008.typ:6-37`). Only 8 knobs; only 2 of them are colors.
- Slots are consumed by components in their `draw` pass: `(ctx.theme.line-items)(ctx, view, body)` (`src/components/line-items.typ:500`), `bank-details` (`src/components/bank-details.typ:143`), `payment-goal` (`src/components/payment-goal.typ:55`), `signature` (`src/components/signature.typ:42`), `document` (`src/components/root.typ:312`). Missing slots get fallbacks via `nest("theme", ensure(..))` (`src/components/line-items.typ:131-133`, `src/components/root.typ:71`).
- The generic line-items renderer already is a de-facto _style + slot recipe_: ~25 flat style params (`color-subtitle`, `stroke-thin`, `cell-inset`, `totals-width`, ...) and ~15 `render-*` hooks with `auto` = default renderer (`src/themes/components/line-items/line-items.typ:6-66`), and exported default sub-renderers (`default-render-subtotal` ... `default-render-tax`, `src/themes/components/line-items/totals.typ:5-164`) which the "elegant" variant calls as _super_ (`src/themes/base-theme/line-items.typ:74-89`). Four unexported look variants exist: elegant/vibrant/luxury/informational (`src/themes/base-theme/line-items.typ:42,242,279,297`) with hard-coded colors (`accent = rgb("#ec4899")`, `gold = rgb("#b8860b")`).
- DIN document wrapper: `set text(font: font)` (`src/themes/DIN-5008/document.typ:80`), hard-coded `set text(10pt)` for the header (`:88`), `set par(justify: true)`/`hyphenate` (`:183-184`), and delegates page setup to `letter-pro.letter-generic` (`:161`).
- Scoped ctx override exists: `apply(..args, body)` = `ctx + args.named()` (`src/loom-wrapper.typ:18-22`) - **shallow**.
- House style of other APIs (relevant for "patch DSL" mechanism): locale = factory closure `build-locale(lang, region)` returning `(..overrides, base-lang, base-region) => ctx` (`src/locale/factory.typ:37-76`); patches are produced by typed helper functions with `auto` defaults that emit `(strings: (group: payload))` fragments (`src/locale/custom.typ:1-25`); merge is a depth-2 "base-pull" merge that **panics on unknown keys** listing the allowed ones (`src/locale/factory.typ:3-35`).

## 2. Part A - Typst ecosystem patterns

### A1. touying (slides) - "config sections + self object + methods"

Pattern [V-src: `src/configs.typ`, `src/utils.typ`, `themes/simple.typ` on GitHub main]:

- A theme is a **function that wraps a show rule** and forwards user args:
  ```typst
  #let simple-theme(aspect-ratio: "16-9", header: self => .., footer: none, primary: aqua.darken(50%), ..args, body) = {
    show: touying-slides.with(
      config-page(..), config-common(..), config-methods(..),
      config-colors(primary: primary, ..), config-store(header: header, footer: footer, ..),
      ..args,            // user-supplied config-xyz(...) come LAST and therefore win
    )
    body
  }
  ```
- Each `config-*()` returns a **namespaced dict fragment** (`(colors: (...))`, `(store: (...))`, `(methods: (...))`, `(page: (...))`, `(info: (...))`); unset params are filtered with a private `_default` sentinel; fragments are folded with `utils.merge-dicts(init, ..dicts)` (recursive, later wins).
- The merged dict is `self`. Slide functions receive `self`; user-facing content slots are **value-or-function**: `utils.call-or-display(self, self.store.header)` calls it with `self` if it is a function, else displays it.
- Colors: fixed semantic vocabulary `primary/secondary/tertiary/neutral` x `light/lighter/lightest/dark/darker/darkest` (28 keys), referenced as `self.colors.primary`.
- "Methods" (`self.methods.cover`, `alert`, ...) are functions stored in the dict that take `self:` as a named arg (late binding); `utils.methods(self)` pre-binds.
- Scoped override: `#show: touying-set-config.with(config-colors(primary: red))` for a range of slides.

Pros for invoice-pro: near-identical to what loom already offers (`ctx` = `self`); namespaced fragments are the same shape as `locale/custom.typ` patches; `..args` last = Tailwind-`extend`-like user layer; `store` = an explicitly _unstable/theme-private_ namespace, which lets the stable vocabulary stay small. Cons: 28 pre-derived color keys are all independent (changing `primary` does not recompute `primary-light`); `self` is a grab-bag with no schema validation; method binding convention (`self: self`) is awkward.

### A2. polylux - "plain functions + state"

Pattern [doc + mem]: a theme = one setup function used with `#show: my-theme.with(..)` (sets page, text, footer) + slide functions that are plain functions. Options shared between setup and slide functions live in `state(...)` and are read inside `context` (e.g. older `clean-theme` kept `clean-color = state(..)`). Header/footer via `set page(header/footer)`.

Pros: minimal. Cons: `state` + `context` makes content opaque (loom could not traverse it - see S2), adds layout iterations, and is unnecessary here because loom already has a scoped ctx. **Not recommended** beyond page-number footers.

### A3. cetz - "style tree with `auto` inheritance and root/base/merge resolution"

Pattern [V-src: local cache `cetz/0.5.1/src/styles.typ:3-160,203-220,265-345,352-368`; V: `PA/c11-cetz-resolve.typ`]:

- One default style dict: root keys (`fill`, `stroke`, `radius`, `mark`, ...) + per-element sub-dicts (`circle`, `line`, `content`, ...) whose keys are mostly `auto`.
- `styles.resolve(ctx.style, root: "line", merge: inline-style, base: element-defaults)`: `base` fills holes, `merge` overrides, then every `auto` (or dict) value **travels up the tree to the nearest ancestor with the same key** (`traverse-up`, `_fold-value`: `top == auto -> bottom`; `none` is a real value, never inherited; dicts merge).
- Strokes are normalised to dicts first (`_stroke-to-dict`) "since Typst does not support merging two stroke types", so `(thickness: 2pt)` folds into the root stroke's paint.
- User API: `set-style(line: (stroke: red))` (scoped to the canvas group), or inline named args per element.

I ran the real cetz resolver on an invoice-shaped tree: root `accent`, `line-items: (accent: auto, header: (accent: auto, fill: auto))`, user patch `(accent: pink, line-items: (header: (fill: yellow)))` -> `line-items.header.accent == pink`, `totals.stroke` folded `(thickness: 2pt)` with root paint [V, `PA/c11.png`].

Pros: exactly the "cascade" the docs promise ("Cascading approach", `docs/docs/api-reference/theme.md:13`); `auto` = inherit, `none` = off is already the house convention (`locale/custom.typ:4-10`, `render-*: auto`). One brand change at the root restyles every part. Cons: the full algorithm is ~150 lines and subtle; same-key-name inheritance is implicit magic (a part key named `fill` inherits the root `fill`, which may surprise); cost scales with tree size x depth (still small).

### A4. fletcher - "diagram-level defaults for `auto` element options"

Pattern [V-src: `src/diagram.typ` signature; resolution fn bodies not inspected]: `diagram(node-stroke:, node-fill:, node-inset:, edge-stroke:, mark-scale:, label-size:, crossing-fill:, ...)` collects an `options` dict; nodes/edges default every style param to `auto` and `resolve-node-options`/`resolve-edge-options` substitute the diagram-level value. Flat, prefix-named keys (`node-*`, `edge-*`) instead of a tree.

Pros: simplest possible two-level cascade, fully discoverable through the function signature (autocomplete works for named params - typst 0.15 added autocompletion for user-function params). Cons: flat prefix names do not scale to ~10 parts x ~10 props; invoice-pro's current `color-row-odd`/`stroke-thin` flat params are already at that limit.

### A5. elembic - "custom elements, set/show rules in pure Typst"

Pattern [doc: Typst Universe page, handbook "Limitations"]: v1.1.1 (2025-07-08), min Typst 0.11.

```typst
#import "@preview/elembic:1.1.1" as e: field, types
#let bigbox = e.element.declare("bigbox", prefix: "@preview/my-package,v1",
  display: it => block(fill: it.fill, stroke: it.stroke, inset: 5pt, it.body),
  fields: (field("body", types.option(content), required: true),
           field("fill", types.option(types.paint)),
           field("stroke", types.option(stroke), default: red)))
#show: e.set_(bigbox, fill: red)      // NOT native `#set`
#bigbox[abc]
```

How: rules are encoded in the style chain via show rules on hidden built-in elements and read back in `context`; typed fields, revoke/reset rules, nested selectors. Cost/limits: normal mode max **~30 non-consecutive rules per scope** (each rule = 2 nested calls towards Typst's show-rule depth limit), "leaky" mode ~60 but resets `set bibliography(title:)`, "stateful" mode unlimited but uses `state` (relayouts, slower); contextual elements lose memoization; syntax is `#show: e.set_(..)`, never `#set`. The author positions it as an experiment to shape future native custom elements (still only _planned_ upstream; typst 0.15 changelog contains no custom elements/types [doc]).

Pros: the only way to get real `set`-like UX for `line-items`, `totals` etc. Cons for invoice-pro: a heavy third-party runtime inside a legally sensitive package; elements resolve inside `context` -> opaque to loom's traversal (same problem as S2); duplicates what loom ctx + `apply` already provides; will be obsoleted by native custom elements. **Not recommended as a foundation**; the _vocabulary_ (fields with types/defaults, `set_`, `revoke`) is good inspiration for a ctx-based equivalent.

### A6. valkyrie - "schema validation with good errors"

Pattern [doc: README, v1.0.0]: `z.parse(value, z.dictionary((field: z.string())))`, types incl. `z.color`, `z.length`, `z.either`, `z.tuple`, optional/default, coercions; hierarchical error messages naming the failing path.

Pros: schema-as-data could double as documentation and as the unknown-key guard. Cons: extra dependency; invoice-pro already has its own `utils/types.typ` (`types.require(form, "theme::DIN-5008::form", "A", "B")`, `src/themes/DIN-5008/din-5008.typ:19`) and the locale factory's "unknown key -> panic with allowed keys" (`src/locale/factory.typ:18-29`). Recommendation: **reuse the in-house validation idiom**, extend the base-pull merge to arbitrary depth; do not add valkyrie.

### A7. tidy - "a style is a module/dict of render functions"

Pattern [doc + mem]: `tidy.show-module(docs, style: tidy.styles.minimal, colors: tidy.styles.default.colors-dark)`. A style is a module (or dict) exposing a fixed set of functions (`show-outline`, `show-type`, `show-function`, `show-parameter-list`, `show-parameter-block`, `show-variable`, `show-example`, ...); users write a custom style by providing the same names, typically importing the default style and overriding a few. Colors are a separate dict parameter.

This is **the same architecture invoice-pro already has** (slot dict) and confirms: (a) slot dict + (b) separate color dict is an established Typst idiom; (c) "import default, override some" is how users customise.

### A8. Letter / invoice templates on Typst Universe (what knobs exist in the wild)

- `letter-pro` 3.0.0 [V-src, local cache]: `letter-generic(format: "DIN-5008-A"|"DIN-5008-B", header, footer, folding-marks, hole-mark, address-box, information-box, reference-signs, page-numbering: auto|str|function|none, margin)` and `letter-simple(.. font: "Source Sans Pro", stamp, annotations, date, subject)`. Geometry is a tiny table `letter-formats = ("DIN-5008-A": (folding-mark-1-pos: 87mm, folding-mark-2-pos: 192mm, header-size: 27mm), "DIN-5008-B": (105mm, 210mm, 45mm))` (`src/lib.typ:18-30`); everything else is **hard-coded**: address zone `pad(left: 20mm)`, `columns: (85mm, 75mm)`, `rows: 45mm`, hole mark `148.5mm`, mark stroke `0.25pt + black`, ref-sign grid `(45.77mm x3, 25mm)`, font sizes 7/8/10pt, EN/DE-only "Page x of y" via `text.lang` (`src/lib.typ:132-245`). No colors at all.
- `appreciated-letter` 0.1.0 [V-src]: same family (`letter-simple`-like signature), no theming knobs beyond font/margins.
- `invoice-maker` [doc]: `invoice.with(language, banner-image: image(..), invoice-id, ..)`, data from `.typ` or `.yaml`; "customize colors and fonts" by editing.
- `classy-german-invoice`, `tiefletter`, `german-fx-invoice`, `inboisu` [doc, listing only]: fixed look, knobs are data + a few toggles (currency format, pro-forma, prepayment).

Take-away: **no Typst invoice/letter package has a real theming API**; typical ceiling = font + one accent color + banner image + margins. A token/slot/geometry API would be a differentiator; the most common real-world asks visible in these packages are _logo/banner image, accent color, font, footer columns, page numbering format, paper (A4 vs US letter)_.

### A9. brilliant-cv / modern-cv - "metadata-driven themes"

- brilliant-cv [doc: configuration reference]: the USER loads `toml("metadata.toml")` in `cv.typ` and passes it as `metadata`; `[layout] awesome_color = "skyblue" | "#1E90FF"` (named presets or hex), `before_section_skip`, `before_entry_skip`, `paper_size`, `date_width`; `[layout.fonts] regular_fonts = [..]`, `header_font`; `[layout.header] header_align`, `display_profile_photo`, `profile_photo_radius = "50%"`, `info_font_size`; `[layout.entry]`, `[layout.section] highlight mode`, `[layout.footer]`. One complete file per profile ("complete, self-contained configuration").
- modern-cv [V-src: `lib.typ`]: `resume(accent-color:, colored-headers:, show-footer:, language:, font:, header-font:, paper-size:, margins:, use-smallcaps:, ..)`; helper functions (`resume-entry(accent-color: ..)`) need the accent passed **again explicitly** because there is no shared context - the exact problem loom's ctx solves.

Take-aways: TOML brand files are accepted by users; lengths/ratios arrive as **strings** and must be parsed; colors as preset-name-or-hex; the user (not the package) performs the file read.

## 3. Part B - Cross-ecosystem patterns

### B1. W3C Design Tokens (DTCG format module 2025.10) [doc]

- JSON; a token = object with `$value` (+ `$type`, `$description`, `$deprecated`, `$extensions`); groups nest arbitrarily; `$type` inherits from the group; aliases `"{group.token}"` (whole-token references) and JSON-pointer `$ref`; groups can `$extends` another group (deep merge); composite types `typography`, `border`, `shadow`, `strokeStyle`, `gradient`, `transition`; dimension `{value, unit: "px"|"rem"}`; color `{colorSpace, components, hex}`. **No theming/modes in the format itself** (a separate resolver draft handles modes).
- The industry _tiering_ convention layered on top: **primitive/reference** tokens (`color.blue.600`, `space.2`) -> **semantic/system** tokens (`color.accent`, `color.text.muted`, `border.rule`) -> **component** tokens (`line-items.header.fill`). Overriding happens at the highest tier that expresses the intent: rebrand = change primitives; tweak one table = change component tokens.

Mapping to Typst [V, `PA/c12-tokens.typ`]: a nested dict whose leaves are (a) plain values, (b) alias strings `"{color.brand}"`, or (c) lazy functions `t => t.color.brand.lighten(92%)`; `resolve()` = deep-merge(defaults, user) then one recursive pass that dereferences aliases/functions against the _merged_ root (depth-limited for cycles). Verified: patching only `color.brand` re-derives `semantic.stripe`, `line-items.header.fill`, and an auto-contrast header text color. Composite tokens map naturally to Typst values (`stroke`, `(font:, size:, weight:)` dict spread into `text(..)`, inset dicts). Units: DTCG px/rem are irrelevant; brand TOML should use Typst unit strings (`"10.5pt"`, `"0.65em"`, `"25mm"`, `"66%"`).

### B2. CSS custom properties, cascade, `@layer`

- Custom properties = tokens resolved **at use site, lazily, by inheritance through the tree** (`var(--accent, fallback)`); a subtree can re-declare `--accent`. Equivalent here: tokens live in loom ctx; a scoping motif re-declares them for a subtree (verified mechanism: `apply(theme: ..)` reaches the subtree's renderer, `PA/c10-apply.typ` [V]).
- Cascade order: origin/layer first, then specificity, then order. `@layer reset, base, theme, components, utilities;` makes precedence **explicit and named** rather than order-of-appearance accidents. Equivalent here: a fixed merge order such as `engine defaults < theme preset < variant < brand (file) < user overrides < scoped apply < inline component args`. Naming these layers in the docs is the cheapest way to make "cascading" predictable.
- Typst's own style chain is a cascade too, but with exactly one rule: innermost wins, and explicit element args beat any set rule [V] - which is why a theme that writes `set text(font: ..)` makes a user's pre-template `#set text(font: ..)` ineffective (`PA/c06-a-1.png`: user asked for Libertinus Serif before `#show: invoice`, output stays Liberation Sans) [V].

### B3. Tailwind `theme` vs `theme.extend`

`theme: { colors: {...} }` **replaces** the default palette; `theme.extend.colors` **deep-merges** into it. Two verbs for two intents, chosen by the key the user writes. Typst analogue: dict patches are merges by default; replacement needs an explicit marker. Options seen in the wild: a wrapper value (`replace((..))`), a `none` to delete then re-add, or separate parameters (`tokens:` merge vs `palette:` replace). invoice-pro's locale already only offers _merge-with-schema-check_; for themes, arrays (e.g. `column-order`, `align-body`) and strokes are the values where replace-vs-merge matters (arrays should always replace; partial stroke/inset dicts should fold like cetz does).

### B4. Material UI `createTheme`

`createTheme({ palette, typography, spacing, shape, components: { MuiButton: { defaultProps, styleOverrides: { root, .. }, variants: [{ props, style }] } } }, ...moreArgsDeepMerged)`. Notable ideas:

- **Seed -> augmented color**: user gives `palette.primary.main`; `light`, `dark` and `contrastText` are _computed_ (`augmentColor`, `contrastThreshold: 3`, `tonalOffset`). Pure-Typst equivalent verified (`PA/c03-color.typ`): `on-color(bg)` picks black/white by WCAG contrast; `ensure-contrast(fg, bg, target: 4.5)` darkens until AA (pink `#ec4899` on white 3.53 -> `#bf3a7c` 5.09) [V].
- **`spacing` is a function/scale**, not a list of lengths (`theme.spacing(2)`). Typst: `space: (unit: 0.4em)` + helper, or a named scale `(xs, sm, md, lg)`.
- **Per-component triple**: `defaultProps` (= change default _arguments_ of a component, e.g. `line-items(column-order: ..)`/`payment-goal(days: ..)`), `styleOverrides` by **slot name** (= part-level style dicts), `variants` (= named presets matched on props). `defaultProps` is interesting for invoice-pro because components are user-called functions (`#line-items[..]`, `#bank-details(..)`) - a theme could supply their default args through ctx (components already read ctx in `scope`).
- Theme composition: `createTheme(base, overrideA, overrideB)` deep-merges left to right; themes can be nested (`<ThemeProvider>` inside another) = scoped apply.

### B5. Chakra v3 / Panda / Stitches "recipes", "slot recipes", "variants"

`defineSlotRecipe({ slots: ["root","control","label"], base: {root: {...}, ...}, variants: { size: { sm: {control: {...}} } }, defaultVariants, compoundVariants })` [doc]. Styles refer to **semantic tokens** by name, never raw values. A component = named **slots (parts)**; a **variant** = a named partial style patch per slot; several variant axes compose (`size` x `visual`), `compoundVariants` handle combinations.

Mapping: invoice parts = `line-items: (table, header, row, item-title, item-description, modifier, totals, total-gross, tax-row, global-info)`; variant axes e.g. `density: compact|regular|relaxed`, `look: plain|striped|boxed|elegant|vibrant`, `totals: right|full-width`. The existing elegant/vibrant/luxury renderers (`src/themes/base-theme/line-items.typ:42-315`) are exactly "variants" expressed as code; most of their differences are data (strokes, insets, fills) and only `render-header`/`render-totals-body` need functions -> variant = `(tokens patch, slot overrides)` pair.

### B6. Docusaurus swizzling - wrap vs eject [doc]

- **Eject** = copy the whole component and own it; **wrap** = `import Orig from '@theme-original/X'` and render `<Orig {...props}/>` with additions. Official advice: "Prefer wrapping whenever possible: the amount of code to maintain is smaller."
- Components are classified **safe / unsafe / forbidden** to swizzle = a _stability contract per slot_.

Typst mapping [V]: `theme + (line-items: (ctx, data, body) => decorate((base.line-items)(ctx, data, body)))` (`PA/c06-setrules.typ`, variant d; generic helper `wrap(theme, slot, (super, ..args) => ..)` in `PA/c02-dict-fn.typ`). Status quo already exports `default-render-*` for totals, i.e. wrap-ability at sub-slot level. The safety classification maps to documenting which slots/ctx fields are **stable** vs **internal** - essential for "lock in v0.5.0", because a slot renderer's real API is the _shape of `ctx` and `data`_ it receives.

### B7. KOMA-Script `scrlttr2` and `.lco` files - the closest domain prior art [doc: scrlttr2-en.tex on CTAN + mem]

scrlttr2 separates **four orthogonal mechanisms**:

| Mechanism                      | Command                                                                                                                                                                                                 | What it holds                                                 | Examples                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Pseudo-lengths** (geometry)  | `\setplength{toaddrvpos}{45mm}`, `\addtoplength`                                                                                                                                                        | absolute positions/sizes of first-page zones                  | letterhead: `firstheadvpos/hpos/width`; address window: `toaddrvpos, toaddrhpos, toaddrwidth, toaddrheight, toaddrindent, backaddrheight, specialmailindent`; location/info field: `locvpos, lochpos, locwidth, locheight`; reference line: `refvpos, refhpos, refwidth, refaftervskip`; fold marks: `tfoldmarkvpos, mfoldmarkvpos, bfoldmarkvpos, pfoldmarkvpos` (punch), `lfoldmarkhpos, foldmarkhpos, *foldmarklength, foldmarkthickness`; first-page footer: `firstfootvpos/hpos/width`; signature: `sigindent, sigbeforevskip`; subject: `subjectvpos, subjectbeforevskip, subjectaftervskip` |
| **Options** (features/toggles) | `\KOMAoptions{foldmarks=blmt, fromalign=right, fromlogo, backaddress=plain, addrfield=true, locfield=wide, subject=titled, refline=dateright, firstfoot=false, pagenumber=botcenter, enlargefirstpage}` | which zones exist and their mode                              |                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| **Variables** (content)        | `\setkomavar{fromname}[label]{content}`                                                                                                                                                                 | data _and its label_, reusable via `\usekomavar`              | `fromname, fromaddress, fromlogo, backaddress, toname, invoice, customer, yourref, place, date, subject, signature, frombank, firstfoot, nexthead`                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **Element fonts** (style)      | `\setkomafont{fromname}{\bfseries\color{..}}`, `\addtokomafont`                                                                                                                                         | per-named-element font/color; `add` = extend, `set` = replace | `addressee, backaddress, fromname, fromaddress, fromrule, foldmark, refname, refvalue, subject, title, pagenumber, pagefoot`                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

An **`.lco` file** ("letter class option") is just a named bundle of those settings, overwhelmingly pseudo-lengths + options: shipped `DIN` (DIN 676/5008, C6/5 & DL window), `DINmtext` (more text on page one), `SN` / `SNleft` (Swiss SN 010130, address right/left), `NF` (French NF Z 11-001), `UScommercial9` / `UScommercial9DW` (US #9 envelope, single/double window), `NipponEL/EH/LL/LH/RL`, `KakuLL` (Japanese envelopes), `KOMAold`. `\LoadLetterOption{DIN}` then `\LoadLetterOption{mycompany}` **stack** - later files patch earlier ones (a cascade of profiles); companies write `mycompany.lco` = "DIN + our logo + our footer + our fonts" and every letter says `\documentclass[mycompany]{scrlttr2}`. This is _the_ established workflow for corporate letter identity.

Why it matters here: invoice-pro's DIN theme conflates what KOMA separates. Geometry (address window position, fold marks, header height) is locked inside letter-pro's hard-coded numbers; style (font, colors) is spread over two functions; content (sender block, footer) is mixed into the document renderer (`src/themes/DIN-5008/document.typ:82-127`). A **geometry profile dict** analogous to `.lco` (`din-5008-a`, `din-5008-b`, `sn-010130-left/right`, `us-letter-#10-window`, `nf-z-11-001`, plain `a4`) is (a) data-only, (b) orthogonal to colors/fonts, (c) the natural partner of the existing `country`/locale region API, and (d) stackable with patches (`geometry: (address: (top: 50mm))`). It requires invoice-pro to own the page frame instead of delegating to letter-pro (letter-generic is ~120 lines, `letter-pro/3.0.0/src/lib.typ:96-252`).

### Suggested precedence ("layers", cf. CSS `@layer`) - for designers to confirm or change

`engine defaults` < `geometry profile defaults` < `theme preset (DIN-5008, ...)` < `variant(s)` < `brand patch (file/dict)` < `user patch fragments (D6)` < `scoped #themed[...]` (D8) < `inline args on a component call`. Native Typst rules sit outside this chain: user rules _inside the body_ beat theme set rules; user rules _before the template_ lose to them (C2d).

### Modern-business requirements surfaced by the prior art (checklist for the concept)

Brand seed color(s) + accessible derived palette (D2); corporate fonts with fallbacks, no availability check possible (C13); logo + letterhead (SVG for ZUGFeRD) with first-page/continuation distinction (D12); multi-column legal footer (company register, VAT ID, bank, managing directors - German "Pflichtangaben"); page x/y in locale language (letter-pro hard-codes EN/DE via `text.lang`, `letter-pro/3.0.0/src/lib.typ:176-180`); country-specific window-envelope geometry (D5); multi-brand / multi-entity via brand files (D7); print concerns (CMYK works today; spot colors/bleed are 0.15+); density/paper variants (A4 vs US Letter); PDF/A-3b constraints on assets (C10); dark-on-light contrast guarantee for table header fills (C7); stability tiers for slots and ctx shapes (B6).
