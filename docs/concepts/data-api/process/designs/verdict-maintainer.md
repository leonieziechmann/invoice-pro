## Fatal flaws

- **C-performance**: Silent sample leak: the precedence keeps the skeleton's value when the data omits a key, so a sample invoice number reaches a final, non-draft e-invoice. Evidence: I removed `invoice-nr` from proto/data/invoice.json and compiled proto/skeleton.typ with --input invoice-pro-data-file. Result: PDF title 'Rechnung MUSTER-0001', no ENTWURF badge, 1 embedded file (factur-x.xml) with <rsm:ExchangedDocument><ram:ID>MUSTER-0001</ram:ID> (BT-1). proto/schema/invoice-pro-1.schema.json has root required = []. The same test on A, B and D gives a draft with 'fehlt: Rechnungsnummer' and 0 attachments. The cause is in C's invoice.typ: `if "invoice-nr" in a { invoice-nr = a.invoice-nr }`, a presence-only override (B's rejected alternative 3).
- **D-contract**: Blocking as proposed, fixable: every invoice, hydrated or not, emits <invoice-pro-result> and loads the contract descriptor at draw time. This is an always-on behaviour change, and it breaks the 'only what the invoice needs' lazy-module convention. Evidence: Template without data, typst 0.14.2 query: 6 metadata elements on base vs 7 on D. A --timings trace of the template on D shows eval of /src/contract/result.typ 4.79 ms including /src/contract/schema.typ 2.29 ms (result.typ:14 `#import "schema.typ" as s`, imported from root.typ's draw). Wall clock: median of 9 runs, 0.572 s (base) vs 0.593 s (D), within noise but consistently higher.
- **D-contract**: Serious: the public namespace freezes 27 names, including generic type constructors named after Typst builtins, and leaks an internal helper. Evidence: dictionary(lib.invoice-data).keys() lists file-key, from-inputs, input-key, amount, any, array, boolean, date, decimal, enum, field, integer, lines, map, percent, period, text, format, result-format, decode, load, values, check, schema, result-schema, reference, batch. `import invoice-data: *` replaces text, array and decimal in the user's scope.
- **B-integrated**: Serious, fixable: invoice()'s parameter defaults are copied into a literal table inside invoice() for the document-key rule, a second source of truth that drifts silently. Evidence: B's diff of src/invoice.typ: hydrate(given, (currency: auto, sender: (:), …, date: datetime.today(), …, tax-mode: "exclusive", tax-exempt-small-biz: false, custom: none), data). If a signature default changes, only non-hydrated invoices follow it. D repeats the pattern in its descriptor (26 default: entries) and admits the risk.
- **A-converter**: Serious: the only way data problems reach invoice()'s validation (errors: "issue") rides on the internal lazy-theme protocol, and the default (panic) gives up the draft preview that the phase-1 facts require for data errors. Evidence: repo/src/hydrate/args.typ:40-44 `with-issues(theme, issues) = (..args) => { let t = theme(..args); t.issues += issues; t }`, joined by invoice.typ:547 `eval-theme.issues + check-data(..)`. The mode works (verified: draft 'ENTWURF · 10 Probleme · keine E-Rechnung', 0 attachments; strict panics with 10). But it makes an internal theme contract public de facto. A itself proposes `invoice(issues:)` as the clean fix, and then the design is no longer 'zero core change'.

## Ideas to graft

- from **B-integrated**: Document vs issuer roles: what identifies one invoice comes from the data only (the skeleton value is a sample that is dropped), and issuer settings are kept unless the data gives them. Parties are replaced as a whole and never deep-merged. (Samples cannot leak with zero skeleton marks (verified on B and D: missing invoice-nr → draft, XML withheld). C shows what happens without it.)
- from **B-integrated**: Implicit slot: the line-items body is the sample, and data rows replace it as ONE bulk motif. Coverage issues for data with no binding point (items without line-items, payment without payment(..)). (Fits 'design by hand, then hydrate' with no edits, and data is never dropped silently.)
- from **B-integrated**: payment(..) composite that writes the existing payment-terms, direct-debit, card-payment, paid and bank-details by the effective method. It emits bank-details only for a transfer (CII-SR-467). (Which payment components exist is data, and dynamic() cannot bind component parameters. One component instead of five data-aware ones. Keep one file: D already forked it.)
- from **A-converter**: Never duplicate invoice()'s defaults: an absent key must fall to the signature's own default. Inside invoice(), do this with one private defaults table that the signature itself references, plus D's explicit-vs-implicit md5 test. (B copies the defaults into invoice.typ and D into the descriptor; both drift silently when a default changes.)
- from **A-converter**: Wappen as a STATIC theme patch chosen at document level from the decoded values (theme.custom.logo(image: wappen(values.recipient))), instead of a draw-time wrap. (Verified: it keeps prints-of page-content false, so the e-invoice 'is it printed' checks (IP-PRINT-03/IP-PERIOD-03) stay active. wrap or custom part sets it true. With D's values(record) this works in the integrated design too.)
- from **A-converter**: An explicit slot marker (`#invoice-data.items[sample]`, or rows: for CSV-mapped arrays) that may sit next to static rows or inside a skeleton group. Without a marker, the whole body is the slot. (Covers fixed base fees (B's O2 / risk 1) without giving up zero-mark hydration. A and C verified mixed static and data rows.)
- from **C-performance**: One pure resolver for both paths: item() measures through the same item-signal the bulk motif uses. Extend the same approach to group, bundle, modifier and prepayment, as a separate internal-refactor PR. (The only real cure for component/data drift. Re-verified byte-identical on 31 zugferd tests, 2 edge documents and the template once tools/ is present; hand-written invoices also get faster.)
- from **C-performance**: A generated equivalence suite (gen.py + eq.sh) that compares the pristine-base hand-written invoice, the new-tree hand-written invoice and the hydrated invoice by md5 (and XML) across kinds × sizes × zugferd on both compilers. (It turns 'byte-identical' into a CI gate and guards the pseudo-contract on calc-item, calc-bundle and unit resolution.)
- from **C-performance**: Region VAT-rate tables exported next to each region's infer-tax, so a data rate like "16%" becomes a data issue instead of a panic. (One source of truth for rates, and no panic path from data.)
- from **D-contract**: Namespace name `invoice-data`, mirroring invoice(data:). (Follows the 'namespace named after the parameter' rule and avoids user shadowing of a bare `data`.)
- from **D-contract**: Per-key descriptor metadata (BT/BG, role, since, doc) generating the JSON Schema and reference docs. Differential conformance fixtures (jsonschema vs decoder) and a codegen run in CI. $id carries only the format major. (Makes phase 2 cheap and catches contract defects: typify found the double unit spelling. Keeping the package version out of $id leaves check-version unaffected.)
- from **D-contract**: The schema's root `required` lists the legally needed keys (invoice-nr, date, recipient, items). A JSON-Pointer `path` and a `status` (ok, draft, unchecked) go into the result record. (Producers learn the contract before compiling, and pipelines can branch on status. C's schema requires nothing at root.)
- from **A-converter**: Data text dates are written explicitly as {"text": ..}, and a bare string is always an ISO date (shared by A, C and D). (Removes the BT-9/BT-20 trap of the Typst API without changing that API.)

## Recommendation

#### Verdict (maintainer lens)

**B's integrated model wins**, with D's name and contract tooling, A's discipline about defaults and design, and C's drift fix as a _separate_ refactor. Do not adopt C's precedence rule: it leaks sample invoice numbers into real e-invoices (verified). Do not adopt D's always-on result.

##### Public API delta for 0.7.0 (all additive, tier: experimental)

1. **`invoice(data: auto)`**, the only hydration entry. It has to sit inside invoice() so that check-data, draft markers, strict and XML withholding see the real values (phase-1 fact).
   - `auto` reads `--input invoice-pro-data` (inline JSON) through an injectable `inputs:`.
   - It also accepts dict, bytes, JSON text, a 0.15 `path`, or a record from `invoice-data.load`.
2. **`invoice(custom: none)`**: optional, sealed `ctx.custom`, so the skeleton can preview its own custom fields. Unsealed by `unsealed()` and `dynamic`.
3. **Root namespace `invoice-data`** (D's name, mirrors the parameter), with a _small_ surface:
   - `format`, `input-key`, `file-key`;
   - `load(read:, inputs:)` for `--input invoice-pro-data-file` through the skeleton's read callback;
   - `decode`/`check` (layout-free);
   - `values(record)`;
   - `schema()`.
   - Leave out `reference`, `batch`, `derive` and the type constructors in 0.7.0. Declared fields can come later in a sub-namespace, never with names that shadow builtins (`text`, `array`, `decimal`).
4. **Root component `payment(..)`** (B's file, one copy).
5. **Label `<invoice-pro-result>`**: plain strings plus `status`. Emitted only for hydrated invoices, or with `--input invoice-pro-result=1` read through injectable inputs. Lazily loaded, never importing the descriptor on non-hydrated invoices.
6. **One-line behaviour change, justified:** `custom: false` in `party-keys`, so party custom bags raise no IP-KEY-01.

##### Semantics

- **Precedence (B/D roles):** document keys come from the data only (the sample is dropped); issuer keys are kept unless given; parties are replaced whole, never deep-merged; design is never data.
  - Implement the 'parameter default' through **one private defaults table referenced by the signature itself**, so there is no copy (fixes B and D).
  - Add D's explicit-vs-implicit md5 test.
- **Slots:**
  - The line-items body is the implicit items slot.
  - An optional explicit marker (`#invoice-data.items[sample]`, A/C) restricts replacement to the marker, so static fee rows survive.
  - Coverage issues for data with no binding point.
- **Errors:**
  - Data problems become class-`data` issues `schema/<JSON Pointer>` (B/C/D), with localized `schema-*` keys.
  - Typst misuse and a wrong format major panic, in the house message style.
  - The schema's root `required` lists the legally needed keys.
- **Encodings:** decimal strings, `"19%"` (bit-exact), ISO dates, `{"text": ..}` for BT-20. Region rate tables sit next to `infer-tax` (C).

##### Design stays in Typst

- There is no expression language and no theme or locale in the data.
- Document the Wappen as a **static, document-level theme patch** chosen from `invoice-data.values(record)` (A). It keeps `prints-of` page-content false, verified.
- Mention the draw-time wrap only as a second option, with its IP-PRINT caveat.

##### Maintenance obligations

- A single spec table drives both the decoder and the JSON Schema. Commit the schema under `src/` with a CI drift check, and add D's differential fixtures.
- Add `tests/data/` with C-style generated md5/XML equivalence pairs: pristine base hand-written vs new tree hand-written vs hydrated, on both compilers.
- Update the exports pin test (`invoice-data`, `payment`), the docs registries, and `LAZY_MODULES` plus a perf-gate entry for a hydrated 300-line invoice.

##### Explicitly out of this PR

These are follow-ups, each with its own justification:

- C's shared `item-signal` resolver for item(), then group, bundle, modifier and prepayment (the real drift cure).
- The format-item refactor, the exact page-count seed, and the keep-together cheaper check (pure performance work).
- The depth-10 collector bugfix (the format caps depth at 8 until then).
- `item(custom:)`.
- Result attachment and bundle batch.

##### Open decisions to hand the maintainer

1. Borderline roles: `notes`, `subject`, `document-type`, `currency`.
2. Implicit vs explicit items slot as the documented default.
3. Default for data errors: issue (recommended) vs panic.
