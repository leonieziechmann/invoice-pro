## Fatal flaws

- **C-performance**: 'Absent key keeps the skeleton value' leaks samples into real invoices and e-invoices, and strict does not catch it. Evidence: judge-user/C/skel.typ + d-norec.json (no recipient, no invoice-nr) with --input invoice-pro-validation=strict: rc=0. factur-x.xml has <ram:ID>MUSTER-1 and BuyerTradeParty Name 'Muster Kunde'. With the full d1.json the sample order-nr 'PO-MUSTER' is printed and sits in BuyerOrderReferencedDocument (BT-13). B, D and A report all three missing items under strict.
- **C-performance**: Missing marks fail silently: no hydrate.items slot ships the sample items; no data: line ignores the input; data payment means without a payment block is ignored. Evidence: skel-noslot.typ + strict: rc=0, 'Rechnung 2026-0100' with the sample rows and Gesamtbetrag 47,60 € instead of 471,96 €. skel0.typ + inline JSON + strict: rc=0, 'Rechnung MUSTER-1'. skel-nopay.typ with means direct-debit: rc=0, 'Bitte überweisen'.
- **C-performance**: null crashes instead of becoming a data issue (claims 'never panics'). Evidence: "sender": null leads to 'assertion failed: variable `invoice::sender`(none) must be of dictionary'. A default pydantic dump leads to 'expected string, found none' at decode.typ:413.
- **B-integrated**: null = 'reset to default' plus crashes on nested nulls make generated phase-2 models unsafe. The canonical file key is unsupported and silently ignored. Evidence: d1-null.json (sender: null, as model_dump() writes) gives a draft with 'fehlt: Name Rechnungssteller:in' (the letterhead is wiped; under validation none it would ship). A full pydantic default dump crashes with 'cannot apply and to boolean and none' (modifier-applicator.typ:66). --input invoice-pro-data-file=d1.json + strict: rc=0, 'Rechnung MUSTER-1'.
- **A-converter**: Hydration requires restructuring the skeleton (base/sample dicts, 6–7 hydrate.\* calls, duplicated payment constants), and a forgotten slot silently ships sample content under the real invoice number. Evidence: judge-user/A/skel.typ needed letterhead+sample dicts, a theme hook and the bank arguments twice. skel-noslot.typ + strict: rc=0, 'Rechnung 2026-0100', Gesamtbetrag 47,60 € (sample items). skel-nopay.typ with direct-debit data: rc=0, 'Bitte überweisen'.
- **D-contract**: (Fixable, not fatal) The schema/decoder agreement breaks on the most common phase-2 payload: kind: null. Evidence: A pydantic v2 model generated from schema/invoice.schema.json gives model_dump(by_alias=True). The schema validates it with 0 errors, but the decoder crashes: "cannot apply 'not in' to none and dictionary" at contract/decode.typ:605. With only kind:null removed, the PDF is md5-identical to the original (a722fd4e…).

## Ideas to graft

- from **D-contract**: One descriptor table (type, BT, role, binding point, since, doc) that drives the decoder, the JSON Schema, the reference docs and the precedence roles, plus a conformance fixture suite and a codegen run (pydantic/TS/typify) in CI. (It is the only route where 'valid for the schema' can be made to mean 'accepted by invoice-pro'. The codegen run found a real defect, and phase-2 bindings get typed models for free.)
- from **D-contract**: null ≡ absent EVERYWHERE, including discriminators (fix kind: null), and a conformance fixture that is a default model dump (pydantic model_dump(), serde Option without skip_serializing_if). (Verified: generated models emit 23–25 top-level nulls plus nested ones. D survives all of them except kind; B wipes the letterhead; B and C crash; A rejects. This is the most common phase-2 payload.)
- from **D-contract / B-integrated**: Roles per key: document (data only, sample dropped) and issuer (skeleton unless data gives it). Parties are replaced whole. Nothing is marked in the skeleton. (Leak-proof by construction (verified: strict reports the missing invoice-nr and recipient on B and D, while C ships MUSTER-1). It needs no restructuring, so it meets 'simply hydrate'.)
- from **D-contract**: Panic with the one-line fix whenever an invoice-pro-data\* input is present but nothing consumed it (D does this for the file key). Extend it to every input key and every design path. (Every other design has a silent path that ships the SAMPLE invoice under strict: B ignores invoice-pro-data-file, C and A ignore inputs without their wiring line.)
- from **B-integrated / D-contract**: Coverage issues: data sections without a binding point (items without line-items, payment without a payment(..) block) become data issues. (Verified: without them, A and C silently print 'Bitte überweisen' for direct-debit data and ship the sample items with the real invoice number.)
- from **B-integrated**: payment(terms, method, bank, creditor-id, ..) composite as the single payment binding point; data chooses the means key by key. (One call previews and hydrates. A's hydrate.payment made me write the bank arguments twice (sample content plus constants).)
- from **A-converter**: An eval-time typed record (A's rec / D's invoice-data.values) plus a party normaliser (A's hydrate.party) as the recommended Wappen pattern: a STATIC theme.custom.logo patch chosen at document level. (It keeps prints-of page-content false, so the e-invoice 'is it printed' checks stay active, which a wrap or part weakens. The normaliser gives the post code whether city is a string or an object (my derive hook had to handle both by hand).)
- from **D-contract**: Declared, typed custom fields (invoice-data.field/enum/date) exported into the skeleton's own JSON Schema, plus a derive hook for data-dependent parameters. (Expressive enough for 'change X by field value' without an expression language in data, and it gives phase-2 bindings typed models of the custom fields.)
- from **B-integrated / C-performance**: invoice(custom:) as the place for sample custom values, merged key by key with data custom. (D lacks it, so a skeleton can only preview custom values through info.get(default:), and theme parts reading ctx.custom see nothing in the preview.)
- from **A-converter / C-performance**: An optional explicit slot inside line-items (hydrate.items / items-slot) for static rows next to data rows; the whole body stays the default slot. (Fixed base fees and fixed discounts are common in skeletons. B and D drop them when hydrating. Making the slot optional keeps the zero-marker default.)
- from **A-converter / C-performance**: Free-text payment terms (BT-20) as an explicit object ({"text": ..} or payment.terms.text); a bare string is always a date (BT-9). (B and D drop BT-20 free text entirely. The explicit object removes the Typst API's str-due-date trap without losing the feature.)
- from **C-performance**: "19%" is checked against the region's known rates and reported as a data issue with the object-form fix; regions export their rates. (The data and the Typst API then mean the same thing: A panics raw, while B and D silently accept 16% as S.)
- from **D-contract**: Result contract on every invoice with its own schema, rates in the input encoding ("19%"), status/exit-code table, e-invoice diagnostics, and an opt-in attachment of the result for one-compile pipelines. (It was the richest and most consistent of the four in my eval. B labels it <invoice-pro:result> with the input format id, and B and C write rates as "0.19".)
- from **C-performance**: Internal speed-ups that need no API change: item() on the shared pure resolver, and the exact page-count seed. (Off-lens, but the skeleton author's edit-compile loop on hand-written previews gets 20–37 % faster, and it removes drift between the bulk motif and item().)

## Recommendation

#### Final design from the user/ecosystem lens

**Base:** D-contract. It already contains B's integration: `invoice(data: auto)`, the document/issuer roles, the `payment(..)` block, the whole-body items slot and the coverage issues. Graft the fixes below onto it. Drop C's precedence model. Do not use A's base/sample restructuring as the main path.

##### Skeleton author (target: an existing invoice hydrates unchanged)

- `invoice(data: auto)`: `auto` reads `--input invoice-pro-data`, so inline hydration needs no code. For files, add one line: `data: invoice-data.load(read: p => read(p, encoding: none))`.
- **Hard rule:** if any `invoice-pro-data*` input is present and nothing consumed it, panic with the one-line fix. Today D does this for the file key; extend it to every key. B, C and A each ship sample invoices silently here.
- Roles from the descriptor:
  - `document` keys come from the data only; the skeleton's value is a sample and is dropped. Missing values are reported by check-data.
  - `issuer` keys keep the skeleton's value unless the data gives one.
  - Parties are replaced whole.
  - Nothing is marked in the skeleton.
- Add `invoice(custom:)` for preview sample values (from B/C), merged key by key with the data's custom.
- Add an **optional** `items-slot()` marker inside `line-items` for static rows next to data rows (from A/C; B's O2). The whole body stays the default slot.
- Coverage issues: items without `line-items`, or payment without `payment(..)`. Data errors become class-`data` issues: draft report, strict panic, XML withheld.

##### Extensibility

- Open `custom` bags on document (sealed), party (reserved print-only key) and item.
- Optional declared, typed fields (`invoice-data.field(..)`), exported into the skeleton's schema.
- A `derive` hook for data-dependent **parameters**.
- Document the Wappen as A's **static** pattern: `invoice-data.values(record)` plus a party normaliser (A's `hydrate.party`) choose `theme.custom.logo(image: ..)` at eval time, which keeps `prints-of.page-content` false. The render-time wrap remains a documented alternative. No expression language.

##### Data format (`invoice-pro/1`)

- One spelling per concept, kebab-case, BT annotations, decimal strings, `"19%"`, ISO dates.
- **null ≡ absent everywhere, including `kind`.** Make `kind` default to `"item"` in the schema so codegen emits `Literal["item"] = "item"`.
- Units: accept any UN/ECE Rec 20 code by pattern, localize the known ones, and keep `{code, display}`. KWH must not be rejected.
- BT-20 free text through `payment.terms.text`; a bare string is always a date (from A/C).
- `"19%"` is checked against the region's known rates and reported as a data issue with the object-form fix (from C).

##### CLI

- Canonical keys: `invoice-pro-data` (inline; at most about 100 KiB, never on Windows) and `invoice-pro-data-file` (any size, stdin through `/dev/stdin` on POSIX).
- TOML/YAML chosen by file extension; the 0.15 `path` value is accepted.
- Batch: parallel processes by default; the 0.15 bundle is experimental.
- Exit-code and status table from D.

##### Phase 2

- Commit the generated input, result and skeleton schemas with a CI drift check.
- Conformance fixtures **including default model dumps** (pydantic `model_dump()`, serde without `skip_serializing_if`). This would have caught D's `kind: null` crash.
- Run codegen in CI.
- `<invoice-pro-result>` on every invoice (`invoice-pro-result/1`), with rates in the input encoding, `status` and diagnostics, plus opt-in `invoice-pro-result=attach`.
- Versioning by major plus minor with `since` annotations.

##### Tier

- Ship `invoice-data` and `payment` as experimental in 0.7.0, and the format as provisional.
- C's internal speed-ups (shared `item()` resolver, exact page seed) are worth taking separately: they speed up the author's preview loop with no API change.
