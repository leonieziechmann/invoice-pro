### D1: a hydrated invoice stops on any problem (Q1, Q39)

- **The default.** `invoice(validation:)` gets the new default `auto`. It means `"strict"` when the invoice is hydrated, that is, when data comes from `data:` or from `--input invoice-pro-data*`. Otherwise it means `"draft"`. An invoice without data therefore behaves exactly as in 0.6.0.
- **Explicit values.** An explicit `"draft"`, `"strict"` or `none` keeps its meaning in both modes. In a skeleton, an explicit `"draft"` is a deliberate choice for debugging. The template and the examples do not set it.
- **The flags.** `--input invoice-pro-validation=draft|strict|none` still wins over the parameter, as in 0.6.0. `=draft` is the debug view: inline markers, the badge, the watermark and the report page, and no XML. `=none` turns the checks off ("off means off": invalid values are dropped silently, and the XML follows `zugferd-errors`). `=auto` is no override, and the parameter decides (patch 0015). Before patch 0015 the flag `=auto` was an error with the hint "Did you mean auto?".
- **Debug without layout.** `data.check(..)` through `typst eval` or `typst query` reports what the decoder finds.
- **The issue class.** Data problems stay class-`data` issues internally. That is what makes the draft a debug view and keeps the result record's `issues`.
- **The stop.** A hydrated invoice stops at the end, once the layout has run. Its one panic lists every problem once: data, legal, theme and layout findings, as many as the draft's badge counts. It ends with the hint `To debug, render the draft with --input invoice-pro-validation=draft: it marks every problem and lists them on a report page, and it attaches no e-invoice.` The last clause appears only when a data problem is among them. Under hydrated strict, the layout's findings (the footer fit, the identity of number and date, a required part that renders nothing, the contrast of a `themed(..)` scope) are recorded as in the draft, but no badge, marker or report is drawn. While any issue is open, root attaches no e-invoice. An invoice without data keeps the strict behaviour and the panic texts of 0.6.0.
- **Unchanged.** The misuse panics and the R7 panics. `zugferd-errors` keeps its default `"panic"`. `resolve-level(.., hydrated:)` resolves `auto`. Its misuse message now names `auto` among the allowed values, and the pin in `tests/validation/strict` follows.
- **Harness.** `run.sh` check 3 became two checks: the default stops with the problem and the hint, and the draft flag gives a draft with 0 embedded files. `misuse/p3.sh` has 47 checks. They cover the default stop, the flags `draft`, `none` and `auto`, an explicit `"draft"` (`misuse/explicit-draft.typ`), the layout's findings in the stop (`misuse/layout.typ`) and the default without data. `payment/p6.sh` and `result/p8.sh` pass the draft flag where they expect a draft. `fuzz/fuzz.py` checks crash-freedom in two modes. In `default`, a fault must end in the deliberate stop with the hint, or in a clean PDF. In `draft`, a fault must give a draft without an embedded file.

This was already the prototype's behaviour (dev. 9): the data's `custom` replaces the skeleton's sample `custom` as a whole, so no sample value can leak (P3). Nothing changed. The concept records it as decided.

This was already the prototype's behaviour. The body of `line-items` is the implicit binding point. ### D4: the root import may grow by at most 1 ms (Q2)

The budget: the root import of an invoice without data may grow by at most 1.0 ms against pristine 0.6.0, on both compilers.

Patch 0014 reduced the import, because every parsed line costs instructions: about 10 k for an average line, about 5 k for a comment line, 10–15 k for a top-level `let` and about 25 k for a closure (micro-benchmarks on 0.15.1).

- The re-entry hook of `invoice()` passes only the 16 design and issuer parameters to `hydrate(..)`. The check for the applied marker moved into the lazy `hydrate.typ`, and `tools/contract/signature.py` now requires exactly every design and issuer parameter.
- The facades `src/public/data.typ` and `src/public/payment.typ` keep every signature, a one-line doc comment and every `/// -> type` line. The full docs moved next to the bodies in `src/contract/api.typ` and `src/components/payment.typ`, which load only when a function is called.
- Root makes one lazy call for the coverage issues and the strict stop. The items slot filters the marker frames once, and its panic text moved to `src/contract/rows.typ`.
- The comments on the shared path and in the region files are shorter.

Patch 0015 added back about 0.2–0.4 M instructions for the deferred stop.

Measured with instruction counts, because neither wall clock nor traces resolve 1 ms. The tool is cachegrind without cache simulation, `--jobs 1`, on an import-only document. The trees are copied under several sets of names of equal length, because every character of the tree's path costs about 0.03 M instructions.

- **In milliseconds.** The pristine import runs 514.51 M instructions on 0.15.1 and 479.46 M on 0.14.2. On a quiet VM it took 113.3–120.3 ms and 124.9–127.6 ms untraced (4.28–4.54 and 3.76–3.84 M instructions per ms). The verifier's final delta is therefore **0.74–0.79 ms on 0.15.1 and 0.90–0.92 ms on 0.14.2**, within 1 ms.
- **The machine matters.** The budget holds while the pristine import takes at most 153 ms (0.15.1) or 139 ms (0.14.2). Verification round 2 measured 165.5 and 183.2 ms on the same VM under load, and at that rate the same counts would be about 1.08 and 1.32 ms. A gate should therefore compare instructions, relative to the import (for example at most 0.8 % of its instructions) or at a fixed reference rate (concept Q3).
- **The timing methods give no verdict.** Amplified wall clock (16 imports per document) and traced exclusive eval move by more than 1 ms in an A/A test with identical code under another folder name.
- **Bytes parsed by the root import.** +17.1 KiB (+6.1 KiB outside comment lines) on the tree of draft 2, and +12 069 B (+5 823 B outside comment lines) on the final tree (measured for this revision, 0.15.1).
- **Outside the budget: the whole invoice without data.** `prototype/examples/handwritten.typ` runs +11.24 M instructions (+0.51 %, about 2.7 ms) on 0.15.1 and +10.26 M (+0.52 %, about 2.55 ms) on 0.14.2 on the final tree. Before patches 0011–0015 it was +10.66 and +10.81 M. Most of it is likely the items slot's loom level (concept §7.3, L9).
- **Not changed.** No required `/// -> type` doc comment of a public function was dropped. The house conventions are kept: eager facades stay small, and bodies load lazily. The editor hints of `data.*` and `payment` now show the short facade docs. The full text lives in the lazy modules and goes to the api-reference pages in S6.

### D5: the template is a skeleton (Q36)

Patch 0013 changes `template/invoice.typ`, which `typst init` installs:

- the one load line `#let record = data.load(read: p => read(p, encoding: none))` and `data: record`;
- one `payment(terms: (days: 14), bank: (..))` block instead of `payment-terms(days: 14)` and `bank-details(..)`, so that the data's `payment` section has its binding point;
- a header section DATA / PROGRAMMATIC. It says how to hydrate the template from a file (`--input invoice-pro-data-file=..`) and inline (`--input invoice-pro-data="$(cat ..)"`), that a hydrated invoice stops on any problem, and that `--input invoice-pro-validation=draft` shows why.

The import line and its version are unchanged. Without data, the template's PDF is byte-identical to the 0.6.0 template on both compilers, with and without `--pdf-standard a-3b`, so the golden XML and the thumbnail stay. It runs more instructions, though: +27.0 M (+1.17 %) on 0.15.1 and +25.7 M (+1.14 %) on 0.14.2 against the 0.6.0 template. That was measured for the concept with cachegrind, `--jobs 1`, one run each, with the trees under names of equal length. Of this, the `payment(..)` block was +16.7 M on the tree of the second draft (concept §7.3).

### D6: canonical names (Q19)

Patch 0011:

- **The namespace.** The root namespace `invoice-data` is now `data`, and its file `src/public/invoice-data.typ` is now `src/public/data.typ`. This follows the house rule that a namespace is named after the parameter it feeds (`theme:`/`theme`, `locale:`/`locale`), so a skeleton writes `invoice(data: data.load(..))`.
- **Dropped constants.** `input-key` and `file-key` leave the public namespace, which keeps 8 names: `format`, `load`, `decode`, `check`, `values`, `party`, `items`, `schema`. The constants stay internal in `src/contract/input.typ`, and the docs name the two `--input` keys instead.
- **Messages and tests.** Every message, comment and test follows (`data: data.load(read: ..)`, `data.items[..]`), and so does the export pin `tests/theme/exports/test.typ`. The marker's internal frame kind is now `data-items`.
- **Kept, because they are canonical already.** `payment`, `custom`, `invoice(data:, custom:)`. The parameter and data-format keys that mirror existing API names (`creditor-id`, `direct-debit`, `show-reference`, `qr-code`, `invoice-nr`, `bank`, …), because consistency with the existing API is the canonical choice. The `--input` keys `invoice-pro-data`, `invoice-pro-data-file` and `invoice-pro-result`, and the label `<invoice-pro-result>`, which follow the house prefix convention.
- **The shadowing caveat.** The second draft argued against `data` for this reason. A file that binds `data` itself after `import *` (`#let data = json(..)`) hides the namespace. `invoice(data: <dictionary>)` still works, but `data.load` is out of reach. The docs therefore name the record `record`. A binding named `data` made before `import *` is replaced by the namespace, as happens with every new root export (concept L5). `misuse/shadow-before.typ` and `misuse/shadow-after.typ` pin both cases. This cannot be fixed in code without giving up the name. `import data: *` shadows no Typst builtin.
- **Not applied.** Two sub-points of the second draft's Q19 are not applied, and the concept lists them for confirmation: renaming `payment(bank:)` to `account` (kept, because `bank` mirrors `bank-details`), and the issue-id prefix `data/…` instead of `schema/…`.

### Still open after this round

- **The extra problem without a recipient** (concept O25, minor). When the data has no recipient, the hydrated stop lists one more problem than the draft: "theme::parts::recipient returned no content, but it carries legally required output". It shows up in 2 of 74 faulty inputs on both compilers (`broken-no-recipient.json`: "found 3 problems" against "ENTWURF · 2 Probleme"). Under hydrated strict the recipient part renders without the draft's markers, so it is empty. The fix is to drop the part-empty finding when a data issue already covers that part, or to run the empty check on the draft rendering (S2).
- **Near misses outside the reserved prefix** (concept O26, older than these patches). `--input invoice-pro-dat=..`, `invoce-pro-data`, `inovice-pro-data`, `invoice-pro-date` and `invoice-pro-file` are ignored silently, so the skeleton or the template renders its samples as a final e-invoice. Under the fail-safe decision this weighs more (concept Q24).
- **Duplicate ids** (concept O16). The hydrated stop now lists each problem once (`bad.json`: stop 6, badge 6), but the result record still counts the mandate issue twice (7).
- **Wording.** `tools/figures/sheets.typ` captions a figure 'validation: "draft" (the default)'. The docs pages that name `"draft"` as the default change with S2 and S6.
- **The D4 margin.** It depends on the machine (about 9 % on 0.14.2 here). The gate belongs to concept Q3.
