New findings:

- A deliberate behaviour change on the non-hydrated path is missing from the builder's deviations. `custom` is now a known party key (src/zugferd/model.typ:350 and :408), so a hand-written 0.6.0 invoice with recipient.custom no longer gets the 'IP-KEY-01 recipient.custom' warning in the e-invoice report. This only shows with zugferd-errors "report"; default-mode PDFs are identical. It is justified by (f), but should be documented as a public-API extension.
- The non-hydrated path is output-identical but not engine-identical. `_items-slot` (line-items.typ) wraps every line-items body in an extra loom motif, so panics inside line items gain one traceback frame ('while calling `intertwine`'). Messages are unchanged, so tytanic's catch-based tests are unaffected. Its cost on invoices without data is a P9 question.
- The builder's deviation #15 explains the template md5 wrongly. ba5d9a49b5de / c7e98da669bc are the template compiled with --pdf-standard a-3b (as in exp/synth), not 'another file location'. The prototype reproduces exactly these md5s; 881821b7318c / 8a1c8b464422 are the same template without --pdf-standard.
- The builder's P2 never exercised 30 test files. Its '313/313 identical (30 expected errors identical)' counts 30 tytanic-catch tests as identical because both trees stop with 'unknown variable: catch' (79 catch sites plus their plain assertions, e.g. tests/country with 90 assertions). My emulation (scripts/p2_catch.py) closes the gap: messages equal, 29 of 30 files render identically, 1 stops identically. Separately, the builder's page comparison is 30-ppi PNG; mine is PDF bytes for 253 tests and SVG for the 30 with two e-invoice attachments.
- Inline transport limit: --input invoice-pro-data=<JSON> fails with 'Argument list too long' (Linux MAX_ARG_STRLEN, 128 KiB per argument) for large invoices, e.g. t-1000.json at 213 KB; b-1000 at 126 KB still works. The file and /dev/stdin routes give identical PDFs. The CLI docs (phase 1) should steer large data to files or stdin.
- tests/integration has 66 test.typ when globbed recursively (60 top-level + 6 nested); the builder's integration.sh only compares the 60 top-level ones. All 66 are identical (59 PDFs + 7 identical errors).
- Minor, by reasoning rather than test: `import *` now also binds `payment` and `invoice-data` at the package root, so a user binding with one of these names defined before the glob import would be shadowed. This is an unlikely compatibility edge.

New findings:

- result.typ `_text` strips \p{Cf} while the XML writer (zugferd/model.typ text-or-none → plain-text) keeps it. BT-1/BT-44 in the result therefore differ from the XML for any invoice number or recipient name with a BOM, ZWSP, soft hyphen, bidi mark or ZWJ (11 of 344 P8 cases). An invoice-nr of only "﻿" gives result invoice-nr null with status ok and an attached e-invoice. Repros: X/p8/docs/r3:invoice-nr-soft-hyphen.json, conf:invoice-nr-bom.
- Required texts made only of XML-invalid C0 controls (U+0001–U+0008, U+000B/C, U+000E–U+001F; U+001C–U+001F are not White_Space) or only of \p{Cf} pass the schema and check(). plain-text() empties the C0 ones in the XML: invoice-nr, name and item name fail the default zfe=panic, and with zfe=report an XML with an empty BT-1 is attached. legal-id/global-id `id` aborts the compile with zfe=report too (party-inputs.typ:63). mandate, vat-id and buyer-reference are dropped silently. Repros: X/ctl/\*.json, sweep tgt4-0348..0351 and tgt4-0418..0421 (both compilers).
- Code points without a glyph abort --pdf-standard a-3b compiles of schema- and check-valid data: unassigned planes U+2FFFD/U+3FFFD/U+EFFFD and private use U+FFFFD, U+100000, U+10FFFC, U+10FFFD in invoice-nr, names, item names, notes and terms text. The round-2 noncharacter rule covers only U+nFFFE/U+nFFFF; U+FDD0–U+FDEF are accepted and compile. Suggestion: reject \p{Cn} and \p{Co} in printed texts, or document the limit. Repros: X/ctl/pua-\*.json.
- Tax rates: the format's percent pattern allows 6 decimals, the e-invoice 4 (rate-digits = 4, IP-DEC-01). A rate such as 19.123456% is check()-valid but stops the default compile on both compilers. This is not documented. Repro: X/fx-rate6.json.
- python-jsonschema (re.search) lets `$` match before a trailing newline: 57 mutations ("EUR\n", dates, decimals) are valid for python and rejected by ajv, pydantic-core and check(). A portable (?![\s\S]) lookahead is rejected by pydantic-core's Rust regex (verified), so the realistic mitigations are maxLength on the fixed-length codes or a note in the docs.
- Typify maps a type-less `const` (result `format`) to serde_json::Value and accepts 'invoice-pro-result/2'. Adding "type": "string" next to each const would type it. The invoice schema's format is typed correctly (InvoicePro1InvoiceDataFormat).
- check() does not predict some data issues that need only the data. For example, document-type self-billed/389 with payment.method direct-debit and a cash discount is check()-valid (also with region: 'de'), but hydration reports schema/payment/method and schema/payment/terms/discount. Missing mandate and last4 are skeleton-dependent and expected to be hydration-only. Repro: X/p8/docs/r3:doctype-389.json.
- Name lines are counted with their ', ' separator: two lines of 2000 characters give 'sender.name has 4001 characters (all lines together)'. A string name of 4000 characters is valid. This is a fencepost in the message and the limit, and the JSON Schema cannot express it (decoder-only, consistent with conf sender-name-lines-total).
- Non-hydrated path change (P2 note): a sender management array fails on pristine 0.6.0 ('cannot join array with content', both compilers) and compiles on proto (frame.typ fix). This is a bug fix: a document that failed now renders.
- The "" leniency is confirmed and documented (deviation 36). 100 documents are check()-valid but schema-invalid (6 conf, 31 mut, 63 tgt4), all "" for a typed optional key. That direction is safe for producers, but it contradicts §3.3's general 'an optional "" is absent' for schema users.
