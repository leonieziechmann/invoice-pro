# Accuracy critique of the data API concept

Reviewer role: critic (accuracy). Reviewed: [`../../README.md`](../../README.md) (the concept) and [`../../prototype/README.md`](../../prototype/README.md), as written on 2026-11-03. Ground truth: the prototype tree (branch `proto` of the exploration, tree `75826b73`; the ten patches applied to `df934a7` give the same tree), [`../prototype/build.md`](../prototype/build.md), [`verification.md`](verification.md), [`../prototype/deviations.md`](../prototype/deviations.md) and the design files under [`../designs/`](../designs/). Compilers: Typst 0.15.1 and 0.14.2. Scratch work: `<session>/critique-accuracy/`.

## Verdict

The concept is accurate in substance. Every `typst` block compiles on both compilers and is typstyle-clean, `run.sh` passes 12 of 12 on both compilers with the stated md5s, the result record of §5.4 is reproduced byte for byte (JSON-equal), and nearly every number traces to the build or verification report. No blocker. One major finding: §3.7 lists a payment rule as checked by the schema and the decoder, but only the hydrated `payment(..)` block checks it. The minor findings are mostly wording, attribution and provenance slips, plus four commands that fail in a fresh directory.

## Findings

### Major

**M1. §3.7: a method without its details is not a schema or decoder rule.** The list opens with "Rules (schema and decoder unless marked)" and includes "a method whose required details are missing (no mandate, no last4) is an issue, and its component is left out". The decoder catches a `direct-debit` object without `mandate` and a `card` object without `last4`. It does not catch `"method": "card"`, `"method": "direct-debit"` or `"method": "paid"` without the details object. python-jsonschema 4.26.0 accepts all three, and so does `check()` on both compilers (`valid: true`, no issue). Only the hydrated `payment(..)` block reports them (`schema/payment/card/last4`, "… is required: the payment method is "card"", the §8.1 example message). A pipeline that relies on `check()` (§5.5, §10.8, phase 2) gets `valid: true` for data that becomes a draft. Fix: mark the rule _hydrated only (payment(..))_. Alternatively, make it a decoder rule (`method` names a method whose details are absent) and add it to the schema as a `dependentSchemas` entry. Either way, add it to Q34's list of what `check()` cannot predict.
