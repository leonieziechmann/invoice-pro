# Research: Prior art and data formats

Phase-1 reader `prior-art` of the data-API exploration (2026-11-02). Facts marked [v] were verified (read or run), [i] are inferences. `<repo>` is the repository root, `<session>` the scratch directory of the exploration (not part of the repository).

## Summary

Typst prior art falls into three patterns. (a) Spread the data into the function: laskutys loads YAML and calls `invoice(..config, data)`, so the data keys are the parameter names. (b) Pass data through a dedicated parameter: invoice-maker uses `data: yaml(..)`, casoon business-templates uses `data: json(..)` plus a typstgen CLI that also writes ZUGFeRD from the same JSON. (c) Load config from TOML and pick a profile with `--input`: brilliant-cv, whose JSON Schema keeps its own sections closed and offers an open `[custom]` section. Typst's official blog uses `json(bytes(sys.inputs.x))`, and the Python, Ruby and Go bindings all pass a dict of strings carrying JSON. So a phase-1 CLI convention of 'one input = one JSON string' carries over unchanged to phase 2. Established models (EN 16931, UBL, CII, GOBL, Stripe, lexoffice, sevDesk, Invoice Ninja) agree on the same structure: two parties (seller/buyer = supplier/customer), lines, allowances and charges at document and line level, a computed tax breakdown and totals, and payment instructions. Naming differs widely: UBL and CII use UpperCamel, lexoffice and sevDesk camelCase, GOBL, Stripe and Ninja snake_case. GOBL and PayPal send money as decimal strings, Zalando as a decimal number, Stripe as integer cents. I checked locally on Typst 0.14.2 and 0.15.1: a JSON number like 12.30 arrives as float 12.3, while the string "12.30" becomes `decimal("12.30")` exactly. Typst can read kebab-case keys with dot access (`d.invoice-nr`). ISO date strings need a converter, because invoice-pro's `to-date` (src/utils/coercion.typ:46) only accepts `datetime`. A string path passed to a package function is resolved inside the package (checked). On 0.15.1 a new `path` type, created in the user's file, crosses the package boundary correctly. On Linux one `--input` value is capped at 128 KiB (131000 bytes worked, 131072 failed), so the CLI needs a file-path input as well as inline JSON. For extensibility, the prior art favours a closed core plus one named open bag (brilliant-cv `[custom]`, GOBL `meta`/`ext`, Stripe `metadata`) over `x-` prefixed keys at the top level. My codegen runs back this up: with `patternProperties ^x-` plus `additionalProperties: false`, the pydantic model generated by datamodel-codegen 0.88 and the Rust types from typify 0.8 reject `x-` keys, and json-schema-to-typescript weakens the root type to an open index signature. All three tools handle kebab-case keys cleanly through aliases or renames. invoice-pro already has a close internal precedent: `theme.custom.from-data` (src/theming/data.typ) is pure data with no eval and no expression language, coerces strings like "66%", reports unknown keys, and takes an `assets:` callback to resolve user paths. Recommendation: kebab-case keys equal to invoice-pro's own parameter names; decimal strings for money, quantities and rates, with numbers accepted as input; ISO 8601 date strings; a required `format` version plus an optional `$schema`; a closed core with a `custom` bag on the document, the parties and the line items; and conditional logic such as a coat of arms per postcode kept in the Typst skeleton, not in the data.

## Key facts

- [v] laskutys (Typst Universe) hydrates by spreading data into named parameters: `invoice(..config, data)` with `config = yaml("config.yaml")` or `sys.inputs`. It uses kebab-case keys, and prices and VAT rates are strings ("1.99", "0.255"). Its docs say date and logo cannot come from a non-Typst file and that sys.inputs values are strings that need JSON parsing. (https://typst.app/universe/package/laskutys/1.0.0)
- [v] invoice-maker accepts `data: yaml(..)` as a new parameter of `invoice`. Its YAML schema mixes kebab-case (invoice-id, issuing-date, due-date, vat-id, postal-code) with camelCase (smallBusiness), uses plain numbers for money, and has no extension mechanism and no version. (https://raw.githubusercontent.com/ad-si/invoice-maker/main/fixtures/example-data.yaml ; https://raw.githubusercontent.com/ad-si/invoice-maker/main/examples/load-yaml.typ)
- [v] casoon typst-business-templates: an invoice is `#invoice(data: json("RE-2026-001.json"), company: json("/data/company.json"))`. It publishes JSON Schema 2020-12 files with $id/$schema and snake_case keys. Money is number, decimal string or {amount, currency}; dates are ISO strings. Totals are precomputed and the build stops if they are off by a cent. Field descriptions cite EN 16931 BT numbers, and if/then/else switches requirements on `tax_model`. The README notes that a package cannot read a logo path from JSON, so bytes must be passed instead. (https://github.com/casoon/typst-business-templates ; https://raw.githubusercontent.com/casoon/typst-business-templates/main/schema/invoice.schema.json ; .../schema/common.schema.json)
- [v] brilliant-cv: its metadata.toml is validated by a JSON Schema (draft-07) with additionalProperties:false on every section the package owns, plus one open top-level `[custom]` section for user data. Editors pick up the schema from a `#:schema` directive, and a profile is chosen with `--input profile=fr`. (https://yunanwg.github.io/brilliant-CV/configuration ; https://raw.githubusercontent.com/yunanwg/brilliant-CV/main/template/metadata.toml.schema.json)
- [v] Typst's official guidance for automated generation is `json(bytes(sys.inputs.customer))` with `typst compile --input customer="$(cat mike.json)"`. sys.inputs values are always strings. (https://typst.app/blog/2025/automated-generation ; https://typst.app/docs/reference/foundations/sys)
- [v] The language bindings (typst-py `sys_inputs: dict[str,str]` plus `json.dumps`, typst-rb, typst-go-wasm) all pass data the same way, through sys.inputs. typst-go-wasm injects structured values directly. (https://pypi.org/project/typst ; https://github.com/actsasflinn/typst-rb ; https://github.com/varunbpatil/typst-go-wasm)
- [v] In Typst, the JSON number 12.30 becomes float 12.3 and a 20-digit integer becomes a float, while `decimal("12.30")` built from a JSON string keeps the exact digits. Same result on 0.14.2 and 0.15.1. YAML and TOML numbers also become floats (12.3). A YAML date becomes the string "2026-11-02"; a TOML date becomes a datetime. (exp/prior-art/t.typ, dec-json.typ, toml-date.typ run with typst eval/query on both binaries)
- [v] Kebab-case JSON keys are reachable with Typst dot syntax (`d.invoice-nr`). The keys `$schema` and `x-acme` are reachable with `.at(..)`. (exp/prior-art/t.typ output: kebab-access "2026-001", schema-key, x-key)
- [v] An ISO date string converts to a datetime via `toml(bytes("d = " + s)).d` or by splitting the string. Both work on 0.14.2 and 0.15.1. invoice-pro's `to-date` accepts only datetime, an array of datetimes, auto or none, so strings need a new coercion step. (exp/prior-art/t.typ ; src/utils/coercion.typ:46-55)
- [v] invoice-pro's `to-decimal` already accepts str, int, float and decimal; it rounds floats to 15 digits and trims them. So decimal strings fit the existing API without changes. (src/utils/coercion.typ:3-19)
- [v] A string path given to a function inside a package resolves relative to the package: `json("data.json")` called in @local/pathtest looks in pkgs/local/pathtest/0.1.0/data.json and fails. Passing bytes (`read(.., encoding: none)`) works. (exp/prior-art/pkg-test.typ compile error output)
- [v] Typst 0.15.1 has a `path` type: `path("data.json")` created in the user's file becomes path("/data.json"), and a package function can `json(p)` it. On 0.14.2, `path` is still the deprecated drawing function. (exp/prior-art/path2.typ (typst 0.15.1 eval -> ["type","path(\"/data.json\")","path","2026-001"]); path-test.typ deprecation warning on 0.14.2)
- [v] On Linux one `--input key=value` argument is capped at about 128 KiB (MAX_ARG_STRLEN): a 131000-byte value worked and a 131072-byte value failed with 'Argument list too long'. A 214 KB invoice cannot be passed inline. Windows CreateProcess allows 32,767 characters and cmd.exe 8,191. (exp/prior-art: typst eval --input data=<N bytes>; https://stackoverflow.com/questions/3205027)
- [v] `--input file=big.json` followed by `json(sys.inputs.file)` in the user's file works when the file is inside --root (relative or root-absolute path) and fails outside root. (exp/prior-art/file-input.typ runs)
- [v] `typst query` is deprecated in 0.15.1 in favour of `typst eval 'query(<l>).first().value' --in file.typ`. (typst 0.15.1 warning output in exp/prior-art)
- [v] EN 16931 is a semantic model of numbered business terms (BT) grouped into business groups (BG): Seller BG-4, Buyer BG-7, Payment instructions BG-16/17, document allowances and charges BG-20/21, totals BG-22 (BT-106..115), VAT breakdown BG-23 (BT-116..121), invoice line BG-25 (BT-126..131, 146, 149, 151..155). Calculation rules include BR-CO-10..17. It has two syntaxes, UBL 2.1 and CII D16B, and ZUGFeRD/Factur-X embed CII. (https://kronenwerk.org/en/developers/en-16931-developer-guide ; https://github.com/khataos/khataos/blob/main/docs/en16931.md ; https://apps.odoo.com/apps/modules/18.0/einvoice_en16931_core_model)
- [v] The OASIS UBL 2.1 JSON representation is verbose and generic: every element is an array of objects, the value sits in `_`, and currency is an attribute (`"PayableAmount":[{"_":100.00,"currencyID":"CAD"}]`). The committee note says it is not optimised for any application. (https://docs.oasis-open.org/ubl/UBL-2.1-JSON/v2.0/cnd02/UBL-2.1-JSON-v2.0-cnd02.html)
- [v] GOBL (Invopop) uses `$schema` URLs (https://gobl.org/draft-0/bill/invoice) and snake_case. Amounts and percentages are decimal strings ("90.00", "20.0%"); numbers are accepted on input but come back as strings. Totals are calculated and any given values are overwritten. Extension points are `ext` (structured regime/addon codes), `meta` (unstructured data for internal tools), `$tags` (scenario keys such as reverse-charge or self-billed) and `$addons`. (https://invopop.mintlify.app/llms ; https://docs.gobl.org/overview/numbers ; https://docs.gobl.org/draft-0/bill/invoice ; https://docs.gobl.org/draft-0/bill/status)
- [v] Stripe: amounts are integers in the smallest currency unit. `metadata` allows up to 50 keys (key ≤40 chars, value ≤500 chars, strings only), and `custom_fields` holds name/value pairs printed on the invoice (name ≤40, value ≤140). (https://docs.stripe.com/metadata ; https://docs.stripe.com/api/invoices/object.md ; https://withone.ai/knowledge/stripe/...)
- [v] lexoffice uses camelCase with `lineItems[].unitPrice{currency, netAmount, grossAmount, taxRatePercentage}` as numbers and voucherDate as an ISO datetime with offset. sevDesk uses camelCase with objectName references, `invoicePosSave`, and dates as dd.mm.yyyy or a timestamp. Invoice Ninja uses snake_case `line_items`, fixed custom slots `custom_value1..4`, and fixed tax slots `tax_name1..3/tax_rate1..3`. (https://raw.githubusercontent.com/api-evangelist/lexoffice/refs/heads/main/openapi/lexoffice-invoices-api-openapi.yml ; https://withone.ai/knowledge/sevdesk/... ; https://invoiceninja.github.io/docs/api-reference/store-invoice)
- [v] Zalando's API guidelines require a closed Money object {amount (number, format decimal), currency (ISO 4217)} and forbid converting it to float. PayPal sends amounts as decimal strings {currency_code, value: "50.00"}. (https://github.com/zalando/restful-api-guidelines/blob/main/chapters/json-guidelines.adoc ; https://dev-toolbox.tech/tools/currency-code-reference/examples/currency-codes-in-payment-systems)
- [v] The OpenAPI vendor-extension convention: any field starting with `x-` is allowed and ignored by standard parsers (`x-oai-`/`x-oas-` are reserved). CloudEvents extension attributes must be lower-case a-z0-9 and should be at most 20 characters. (https://redocly.com/learn/openapi/openapi-visual-reference/specification-extensions ; https://github.com/cloudevents/spec/blob/v0.3/spec.md)
- [v] Codegen with kebab-case keys works in all three tools. json-schema-to-typescript 15.0.4 keeps quoted keys (`"invoice-nr": string`). datamodel-codegen 0.88.0 produces `invoice_nr: str = Field(alias='invoice-nr')` and maps `format: date` to Python `date`. cargo-typify 0.8.0 produces `#[serde(rename = "invoice-nr")] pub invoice_nr` and maps `format: date` to chrono NaiveDate. (exp/prior-art/codegen/{ts/invoice.d.ts, py/model.py, rs/invoice.rs})
- [v] A top-level `patternProperties: {"^x-": {}}` combined with `additionalProperties: false` breaks codegen. Pydantic uses extra='forbid' and rejects `x-acme` (verified by validating an instance), typify uses deny_unknown_fields, and TypeScript collapses the root interface to `[k: string]: unknown`. A named `custom` object (additionalProperties: true) works everywhere: dict[str, Any], serde_json::Map, {[k]: unknown}. (exp/prior-art/codegen/py/check.py output 'x- REJECTED ... extra_forbidden'; rs/invoice.rs:60-64; ts/invoice.d.ts)
- [v] Pydantic models generated from kebab-case keys can only be constructed by Python field name (invoice_nr=...) when the `--allow-population-by-field-name` option is used; with it, the generated models get populate_by_name=True. (exp/prior-art/codegen/py/check.py + model2.py)
- [v] invoice-pro has a pure-data loader for brand themes, `theme.custom.from-data(data, assets: p => image(p))`: no eval, no expression language, string coercion ("#hex"→rgb, "10pt"→length, "66%"→ratio, "none"→none), unknown keys reported. The `assets:` callback resolves paths relative to the user's file because packages cannot open user paths on 0.14. (src/theming/data.typ:1-60 ; src/invoice.typ:224)
- [v] invoice-pro's party dictionaries are a closed set of known keys. Unknown keys are collected as `input-keys` (with alias and misspelling hints) and reported by the ZUGFeRD rules engine, so a `custom` key inside sender/recipient would be reported unless it is added to the known keys or removed before hydration. (src/zugferd/model.typ:451-500 ; src/zugferd/rules/engine.typ:611-619 ; src/zugferd/keys.typ:1-40)
- [v] invoice-pro already has `dynamic(..)`, which reads a context value by path ("recipient.zip"-style) or runs a closure `ctx => content`. This is an existing hook for presentation logic that depends on data, such as a coat of arms per postcode. (src/components/dynamic.typ:21-36,150-165)
- [v] invoice-pro's public API is kebab-case: invoice(sender, recipient, delivery-address, payee, tax-nr, date, service-period, invoice-nr, customer-nr, order-nr, due-date, payment-reference, notes, tax-mode, …) and item(name, description, quantity, base-quantity, unit, date, price, total, input-gross, tax, item-id, …). (src/invoice.typ:44-214 ; src/components/item.typ:80-120)
- [v] Mustache is logic-less: it has only sections (rendered when a value is truthy or for each list item) and inverted sections, with no if/else, so derived values must be computed beforehand. Handlebars adds registered helpers and Jinja adds filters and tests. The usual advice is to keep business logic out of templates and allow only presentation logic. (https://manpages.ubuntu.com/manpages/noble/en/man5/mustache.5.html ; https://stackoverflow.com/questions/25939324 ; https://dev.to/cocoroutine/truth-about-template-engines-3a7)
- [v] SchemaVer (MODEL-REVISION-ADDITION) is a versioning scheme for data schemas. Adding an optional field to a closed schema is an ADDITION; opening a schema with additionalProperties:true makes later field additions REVISIONs. (https://docs.snowplow.io/docs/api-reference/iglu/common-architecture/schemaver)
- [v] Typst's `decimal` type keeps 28–29 significant digits, refuses mixed float/decimal arithmetic, and is recommended for currency. It should be built from strings. (https://typst.app/docs/reference/foundations/decimal)

## Implications

- DATA FORMAT NAMING: use kebab-case keys identical to invoice-pro's existing Typst parameter and dict-key names (invoice-nr, due-date, sender, recipient, payee, delivery-address, items[].base-quantity, item-id, …). Hydration then becomes a mechanical spread (`invoice(..doc)`, `item(..line)`), like laskutys's `..config`, and needs no renaming table. Typst reads kebab keys natively. Codegen tools map them to snake_case or camelCase through aliases and renames (checked for TS, pydantic and typify). Put EN 16931 BT/BG numbers in the schema (`description`, or an annotation keyword such as `x-en16931: "BT-1"` on the schema, not in the data), as casoon does. Do not use camelCase (lexoffice/sevDesk style) and do not use BT numbers as data keys (UBL-JSON verbosity).
- MONEY, QUANTITIES, RATES: canonical form is a decimal string ("12.30", "2", "0.5"), as in GOBL, PayPal and laskutys. JSON numbers are accepted as a convenience and coerced by the existing `to-decimal`, but the schema documents strings, because Typst turns every JSON number into a float (12.30 becomes 12.3; checked). For percentages use a "19%" string, matching GOBL and invoice-pro's own from-data coercion of "66%" to a ratio. Currency stays document-level ISO 4217 (`currency`), not a per-amount Money object, to stay close to the existing invoice(currency:) API.
- DATES: ISO 8601 `YYYY-MM-DD` strings (`format: date` in the schema, which gives date and NaiveDate types in codegen). Ranges are {start, end} objects or a 2-element array that maps to invoice-pro's `(datetime, datetime)`. This needs a new string-to-datetime coercion; `to-date` currently rejects strings. A one-line TOML-based or split-based parser works on 0.14 and 0.15 at about 5 µs per value (2000 conversions added about 10–15 ms).
- VERSIONING: add a required machine-checked field such as `"format": "invoice-pro/1"` (or `version: 1`) that the Typst hydrator asserts. Typst cannot run JSON Schema, so `$schema` is only an editor hint. Also allow an optional `$schema` URL for editor completion, with the YAML `# yaml-language-server: $schema=` modeline and the TOML `#:schema` directive as equivalents. Version the data format independently of the package semver, with SchemaVer-style rules: new optional fields keep the major, renames and removals bump it.
- EXTENSIONS: core objects are closed (unknown keys are reported, consistent with invoice-pro's existing unknown-key checks for parties and from-data), plus a reserved open `custom` object at document level, on each party and on each line item or bundle (brilliant-cv `[custom]`, GOBL `meta`, Stripe `metadata`). Do not use top-level `x-*` patternProperties: they break the generated pydantic and typify models (checked). The hydrator must remove `custom` from party dicts before calling invoice(), or invoice-pro must whitelist it, because the ZUGFeRD model reports unknown party keys (src/zugferd/model.typ:465). It should then expose custom data to the skeleton, for example through `dynamic`'s ctx or a resolver callback.
- CONDITIONAL/DERIVED VALUES (coat of arms by postcode): keep the data declarative. The data carries facts (post-code, or a precomputed discriminator such as custom.region: "BY"); the Typst skeleton owns the rules (lookup dicts or functions, e.g. `dynamic(ctx => crest-for(ctx.recipient))`). This follows Mustache's 'precompute in the producer' rule and invoice-pro's existing 'No expression language' / 'no eval' rule (src/theming/data.typ:2,7). Assets such as crest images are referenced by key or path in the data and resolved in the user's file through an `assets: p => image(p)` callback (the from-data precedent) or a Typst 0.15 `path`, because packages resolve string paths package-relative (checked).
- HYDRATION API SHAPE: accept a dictionary that is already parsed (works for json/yaml/toml loaded by the user, and for embedders that inject structured sys.inputs), plus bytes or str (inline JSON). Never take a bare path string, because it resolves inside the package. Offer a CLI convention with two inputs: inline JSON (`--input invoice=<json>`) and a file (`--input invoice-file=<path inside --root>`, loaded by `json(..)` in the user's template, or a 0.15 `path`). Inline is capped at about 128 KiB per argument on Linux, about 32 KiB on Windows and 8 KiB in cmd.exe.
- TOTALS: never required in the input; invoice-pro computes them. An optional `expected` block (casoon-style cent check) can catch disagreements between producer and template. GOBL instead overwrites totals silently.
- SPEED: JSON decoding is cheap: a 214 KB, 2000-line JSON parses in about 17–19 ms of total `typst eval`, and decimal plus date coercion of all lines adds about 10–15 ms. Format design will not be the bottleneck; the loom passes and layout will be. Prefer flat, explicit data (no `auto` inference loops) so the hydrator can map one-to-one without extra passes.
- PHASE 2: publish one JSON Schema (2020-12 with `$defs` worked in all three codegen tools) as the single source of truth. Keep it codegen-friendly: closed objects, named `custom` bags, `const` or `enum` for discriminators, few oneOf/if-then-else (typify warns JSON Schema is 'hostile' to type translation). With the phase-1 contract 'one sys.inputs key = one JSON document', typst-py, typst-rb and go-wasm bindings just `json.dumps` a generated model; no binding-specific protocol is needed.

## Risks

- Float precision: if producers send JSON numbers (Stripe- or lexoffice-style), Typst turns them into float and drops trailing zeros (12.30 becomes 12.3; checked). `to-decimal` rounds to 15 digits, which works for typical invoices, but large or high-precision values (above 2^53, or more than 15 significant digits) silently lose digits. The schema should document strings, and the hydrator could warn on numeric money.
- Paths in data do not resolve when read inside the package (checked). Logos, crests and data files referenced by a path string must be resolved in the user's file (callback, bytes, or a 0.15 `path`). Otherwise users hit confusing 'file not found in package dir' errors.
- Inline `--input` JSON is capped at about 128 KiB per argument on Linux (checked), about 32 KiB on Windows CreateProcess and 8191 characters in cmd.exe. A CLI design that only supports inline JSON fails for large invoices or on Windows.
- An open `custom` bag inside party dicts collides with invoice-pro's closed-world unknown-key reporting for parties (src/zugferd/model.typ:465-500). Without stripping or whitelisting, every custom field would produce e-invoice validation issues.
- `x-*` keys at the top level, or patternProperties combined with additionalProperties:false, produce generated Python and Rust models that reject those keys (checked). Phase-2 bindings would then be unable to round-trip extension data.
- Kebab-case keys force aliases in every binding. Generated pydantic models need `--allow-population-by-field-name` to be constructible with snake_case names (checked). TypeScript users must write `obj["invoice-nr"]`. It is a moderate ergonomics cost and is outweighed by the 1:1 mapping to the Typst API.
- Schema drift: Typst cannot execute JSON Schema, so validation lives twice (JSON Schema for producers, Typst-side checks for the hydrator). Without a test that validates the example fixtures against both, the two will diverge.
- Expression creep: users will ask to put conditions in JSON (e.g. 'if post-code starts with 8 then crest X'). Supporting that would require Typst `eval` of strings, which is not file-sandboxed (src/theming/data.typ:2), hurts speed and caching, and breaks phase-2 type safety.
- YAML and TOML inputs behave differently: YAML dates become strings and TOML dates become datetimes, and all numbers become floats (checked). If the format is advertised as 'JSON/YAML/TOML', the coercion layer must handle datetime as well as ISO strings, and strings as well as floats.
- `typst query` is deprecated in 0.15.1 (checked). Any phase-1 tooling that extracts metadata (e.g. a schema dump or validation report) should use `typst eval` but must still support 0.14, where `eval --in` may differ.

## Open questions

- Should the top level of the data mirror invoice() parameters exactly (flat: invoice-nr, sender, recipient, items…), or group them like EN 16931 and GOBL (document / parties / lines / payment)? A flat structure makes the spread hydration trivial; grouping is more self-describing for phase-2 users.
- How should line structure (bundle, group, discount, surcharge, prepayment) appear in data? Options: one `items` array with a `type` discriminator (lexoffice `type: custom|text`, GOBL lines and discounts as separate arrays), or nested `children` for bundles. This affects codegen, because a discriminated oneOf is harder for typify.
- How should percentages be written: "19%" (GOBL, and invoice-pro's from-data) or "0.19" (laskutys, invoice-maker) or 19 (lexoffice taxRatePercentage)? And should tax be given as a rate plus EN 16931 category code (S/Z/E/AE…) or as invoice-pro's `tax.*` presets by name?
- Should the format allow 'slots' in the skeleton (data overrides only selected fields of a hand-built invoice), or must the data be a complete invoice? This decides merge semantics: deep merge vs replace for parties, append vs replace for items.
- Should YAML and TOML be officially supported input formats, or JSON only, with YAML and TOML left as 'works because Typst parses it'?
- Where should the published JSON Schema live (a URL on the docs site with a version in the path, e.g. /schema/invoice-data/1/…json) and how should it be generated (hand-written, or derived from Typst-side descriptors to avoid drift)?
- Should `custom` be allowed on every object, or only at document, party and line level (Stripe and GOBL limit metadata to top-level objects plus lines)?
- Should the hydrator accept EN 16931 BT aliases (e.g. `bt-1`) as an optional input dialect for producers that already have an EN 16931 model? Probably not in phase 1.

## Measurements

- Number and date handling (both compilers): `bin/typst query --root exp/prior-art t.typ "<r>" --field value --one --input 'data={"a":"1.50","b":[1,2]}'` → price-num float "12.3" (input 12.30); decimal("12.30") kept; 12345678901234567890 → float 1.2345678901234567e19; `d.invoice-nr` works; the TOML trick parses "2026-11-02" to datetime(2026,11,2); the sys.inputs JSON decodes. typst-0.14.2 gives identical output.
- YAML/TOML: `yaml(bytes("p: 12.30\nq: '12.30'\nd: 2026-11-02"))` → (p: 12.3, q: "12.30", d: "2026-11-02"); `toml(bytes("date = 2026-11-02 …"))` → datetime, "12.30" string, 12.3 float (typst 0.15.1).
- Package path resolution: `typst compile --root exp/prior-art --package-path exp/prior-art/pkgs pkg-test.typ` → error: file not found (searched at …/pkgs/local/pathtest/0.1.0/data.json). Bytes via `read("data.json", encoding: none)` passed into the package work.
- Typst 0.15 path type: `typst eval --root … --package-path … 'query(<r>).first().value' --in path2.typ` → ["type","path(\"/data.json\")","path","2026-001"]; the package's json(p) resolves relative to the user's file.

Other sources:

- OASIS UBL 2.1 JSON: `"LegalMonetaryTotal":[{"PayableAmount":[{"_":100.00,"currencyID":"CAD"}]}]`. Every element is an array of objects with the value in `_`. The committee note says it is "not streamlined nor optimized for any particular application's objectives". https://docs.oasis-open.org/ubl/UBL-2.1-JSON/v2.0/cnd02/UBL-2.1-JSON-v2.0-cnd02.html
- GOBL: `$schema: https://gobl.org/draft-0/bill/invoice`, snake_case. "GOBL will always parse and serialise amounts and percentages as strings … numbers are not allowed … except for counters or indexes" (https://docs.gobl.org/overview/numbers). Percentages end in `%` ("10.0%"). Totals are calculated and any given totals are "recalculated and silently replaced" (https://invopop.mintlify.app/llms). Extension points: `ext` ("additional structured data specific to the regime or addon"), `meta` ("unstructured data useful for internal tools"), `$tags` (scenario keys: simplified, reverse-charge, self-billed, partial), `$addons`. GOBL prefers readable keys over abstract codes (`credit-transfer` instead of UNTDID 4461 code 30).
- Facturion `@facturion/invoice`: a "simplified-JSON" model covering all of EN 16931, snake_case (document_allowances, base_amount, vat_category_code), shipped with a JSON Schema, Ajv validators (strict and partial) and TypeScript types generated from the schema. It states allowance amounts explicitly ("resolved amount is the operative value"). https://npmjs.com/package/@facturion/invoice
- Beliq covers 121 of the 164 EN 16931 BTs with camelCase fields (Invoice.number, issueDate, currencyCode, dueDate, paymentTerms, taxSummary for BG-23). https://docs.beliq.eu/compliance/field-coverage
- The kamerozkan Peppol generator requires quantities, prices and tax rates as JSON strings ("19.00"), ISO dates, ISO 4217/3166 codes and UNECE units. https://github.com/kamerozkan/peppol-ubl-invoice-generator-sample
- sevDesk: camelCase, `invoicePosSave`, objectName references, invoiceDate as dd.mm.yyyy or timestamp, response sums as strings. lexoffice: `lineItems[].unitPrice{currency, netAmount, grossAmount, taxRatePercentage}` as numbers. Invoice Ninja: snake_case with fixed slots `custom_value1..4` and `tax_name1..3`, an inflexible pattern.

Common structure across all of them: header (number, dates, currency, type, references) → two main parties (seller/buyer) plus optional payee, deliver-to and tax representative → lines (item name/desc, qty+unit, net price, tax category+rate, line allowances) → document allowances and charges → computed totals and tax breakdown → payment instructions and terms → notes. invoice-pro's API already follows this shape with its own kebab-case names.

#### 3. Extensibility patterns

| Pattern                             | Example                                                                                                                                    | Pros                                                                                                      | Cons                                                                                                                |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `x-` prefix on any object (OpenAPI) | `x-internal-id`; "value can be null, a primitive, an array or an object"; `x-oai-`/`x-oas-` reserved                                       | familiar, can sit anywhere                                                                                | breaks codegen when combined with additionalProperties:false (checked, §7); the key-shape rule is easy to get wrong |
| Named open bag                      | brilliant-cv `[custom]`, GOBL `meta`, Stripe `metadata` (strings, 50 keys)                                                                 | typos in the core are still caught; easy to type in codegen (`dict[str, Any]` / `Map` / `{[k]: unknown}`) | one more nesting level                                                                                              |
| Registered structured extensions    | GOBL `ext` (keys defined by regime/addon), `$addons`                                                                                       | validated, interoperable                                                                                  | needs a registry                                                                                                    |
| Scenario tags                       | GOBL `$tags: ["reverse-charge"]`                                                                                                           | declarative switches that change processing                                                               | semantics live in code                                                                                              |
| Fixed custom slots                  | Invoice Ninja `custom_value1..4`, Stripe `custom_fields` (displayed name/value pairs)                                                      | simple to print as generic "extra fields"                                                                 | arbitrary limits, untyped                                                                                           |
| CloudEvents extension attributes    | lower-case a-z0-9, ≤20 chars, top-level                                                                                                    | portable across protocols                                                                                 | flat namespace                                                                                                      |
| JSON Schema mechanics               | `additionalProperties:false` = closed; `patternProperties` for prefixes; `unevaluatedProperties` (2019-09+) when composing with allOf/$ref | standard                                                                                                  | 2019-09+ features are less widely supported in codegen                                                              |

Versioning:

- Self-identifying `$schema` URL (GOBL `draft-0`, casoon). In YAML use the modeline `# yaml-language-server: $schema=…`; in TOML use Taplo's `#:schema …` (https://github.com/bezhermoso/shibboleth.nvim).
- SchemaVer MODEL-REVISION-ADDITION (https://docs.snowplow.io/docs/api-reference/iglu/common-architecture/schemaver): closing objects (additionalProperties:false) keeps later additions as ADDITIONs. Opening them turns new fields into REVISIONs, which is one more reason to confine openness to a `custom` bag.
- brilliant-cv adds migration errors for removed fields, a good pattern for a future `format: invoice-pro/2`.

#### 4. Conditional and derived values (coat of arms by postcode)

- Mustache is logic-less: sections and inverted sections only, "no if statements, else clauses, or for loops", so the producer must precompute values (https://manpages.ubuntu.com/manpages/noble/en/man5/mustache.5.html).
- Handlebars adds registered helpers; its `if` takes only a value, not an expression. Jinja, Liquid and Nunjucks are "semi-logic" with filters (https://dev.to/cocoroutine/truth-about-template-engines-3a7).
- The consensus is: no business logic in templates, some presentation logic allowed (https://stackoverflow.com/questions/25939324).
- In Typst the skeleton is a full program, so the natural split is: **data = facts, skeleton = rules**. invoice-pro already has:
  - `dynamic(ctx => …)` / `dynamic("recipient.zip")` (src/components/dynamic.typ:21-36), a closure over the invoice context;
  - the from-data rule "No expression language … (a file cannot write `t => ..`)" and "no eval (eval is not file-sandboxed)" (src/theming/data.typ:2,7).
- Suggested coat-of-arms pattern (illustrative, not tested against invoice-pro):
  ```typ
  #let crests = (BY: "crests/bavaria.svg", BE: "crests/berlin.svg")
  #let crest-for(r) = { let key = r.at("custom", default: (:)).at("region", default: none); if key in crests { image(crests.at(key)) } }
  // or by postcode prefix: #let crest-for(r) = if r.post-code.starts-with("8") { image("crests/bavaria.svg") }
  #dynamic(ctx => crest-for(ctx.recipient))
  ```
  The data stays plain: `{"recipient": {"name": "…", "city": "80331 München", "custom": {"region": "BY"}}}`.
- Do not put expressions or `eval` strings in JSON. Optionally allow a declarative lookup in the skeleton API (e.g. `hydrate(data, derive: (crest: ctx => …))`), but keep it on the Typst side.

#### 5. Phase-2 readiness: codegen

Tools: datamodel-code-generator (JSON Schema → pydantic v2, dataclasses, TypedDict, msgspec; https://github.com/koxudaxi/datamodel-code-generator), json-schema-to-typescript (https://npmjs.com/package/json-schema-to-typescript; `tsType`, `additionalProperties` default true), typify (https://github.com/oxidecomputer/typify; additionalProperties:false → `deny_unknown_fields`; a schema-valued additionalProperties → `#[serde(flatten)]` map; `format: date` → chrono NaiveDate; "JSON Schema is … hostile to translation into constructive type systems"), quicktype (many languages; https://github.com/quicktype/quicktype).

Experiment results are in §7. Codegen-friendly schema rules:

- closed objects, with openness only in named `custom` bags;
- decimals as `{type: string, pattern: ^-?[0-9]+(\.[0-9]+)?$}` under `$defs/decimal` (generated as `Decimal = string` in TS, a constrained str RootModel in pydantic, a newtype String in Rust);
- `format: date` for dates (gives native date types in Python and Rust);
- `const` / `enum` for version and type discriminators (typify maps `const` to serde_json::Value; enums are cleaner);
- few `oneOf` / `if-then-else` (casoon uses if/then/else; that works for validation but not for codegen).

#### 7. Codegen experiments (<session>/exp/prior-art/codegen/)

Schema: 2020-12, root closed (`additionalProperties:false`) + `patternProperties {"^x-":{}}`, kebab-case keys (`invoice-nr`, `vat-id`, `base-quantity`), `$defs/decimal` string pattern, `date` with `format: date`, open `custom` object, `format` const `"invoice-pro/1"`.

- **TypeScript** (json-schema-to-typescript 15.0.4, `npx json2ts`): `"invoice-nr": string; "vat-id"?: string; "base-quantity"?: Decimal; custom?: {[k: string]: unknown}`. Because of `^x-`, the root interface gets `[k: string]: unknown`, so typos at the root are no longer caught by the type checker.
- **Python** (datamodel-codegen 0.88.0, pydantic v2): `invoice_nr: str = Field(..., alias='invoice-nr')`, `vat_id … alias='vat-id'`, `field_schema … alias='$schema'`, `date: date_aliased | None`, `custom: dict[str, Any] | None`, `extra='forbid'`. Validating `{…, "x-acme": {…}}` → **"x-acme Extra inputs are not permitted"**. The `custom` bag round-trips with `model_dump(by_alias=True)`. Constructing by Python name (`invoice_nr=`) fails unless `--allow-population-by-field-name` is used (then populate_by_name=True).
- **Rust** (cargo-typify 0.8.0): `#[serde(deny_unknown_fields)] pub struct InvoiceData { pub custom: serde_json::Map<..>, pub date: Option<chrono::naive::NaiveDate>, pub format: serde_json::Value, #[serde(rename = "invoice-nr")] pub invoice_nr: String, … pub schema: Option<String> }`. `deny_unknown_fields` means `x-*` keys are rejected; `Decimal(String)` newtype; kebab → snake via rename.

Conclusion: kebab-case is fine for phase 2. Extension data belongs in a named bag, not in `x-*` keys at the root.

   ```json
     "custom": { "campaign": "Q4" }
   }
   ```
2. **Naming**: kebab-case, equal to the Typst parameter and key names, so hydration is `..spread`. EN 16931 BT/BG numbers go in schema annotations and descriptions only.
3. **Numbers**: decimal strings for money, quantities and rates; percentages as "19%"; JSON numbers are tolerated and coerced (with a documented precision caveat).
4. **Dates**: `YYYY-MM-DD` strings; periods as `{start, end}` (or `[start, end]`); add a string → datetime coercion step.
5. **Versioning**: a required `format: "invoice-pro/<major>"` checked in Typst; optional `$schema` for editors; SchemaVer-style evolution; migration errors for removed fields.
6. **Extensions**: closed core plus a `custom` bag on document, party and line. The hydrator strips `custom` before calling invoice()/party normalization and exposes it to the skeleton (dynamic ctx / callbacks). No `x-*` keys at the root, no expressions.
7. **Derived values**: Typst-side resolvers (`dynamic(ctx => …)`, lookup dicts). Assets are resolved in the user's file (`assets: p => image(p)` as in from-data; 0.15 `path` later).
8. **Transport (phase 1 CLI)**: `--input invoice=<json>` (small, at most about 100 KiB on Linux and about 30 KiB on Windows) and `--input invoice-file=<path in root>`. The hydrator accepts dict, bytes or str. The template stub shipped with the package performs `json(..)` in the user's file.
9. **Totals**: computed by invoice-pro; optional `expected` totals for a cross-check.
10. **Phase 2**: one JSON Schema 2020-12 file shipped in the repo (and on the docs site), generated or tested against example fixtures. Bindings `json.dumps` generated models into the same sys.inputs key.
