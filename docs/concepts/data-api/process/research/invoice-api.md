# Research: invoice() and the data it accepts

Phase-1 reader `invoice-api` of the data-API exploration (2026-11-02). Facts marked [v] were verified (read or run), [i] are inferences. `<repo>` is the repository root, `<session>` the scratch directory of the exploration (not part of the repository).

## Summary

invoice() (src/invoice.typ:44-218) takes 33 named parameters plus a positional `body`. Of these, 25 are per-invoice DATA, 7 are DESIGN/CONFIG (theme, locale, references layout, zugferd, zugferd-errors, validation, tax-mode), and one is the deprecated tax-nr. Every parameter is type-checked at the boundary with `types.require` (invoice.typ:220-371). I spread a JSON dictionary of str/null/bool/array/dict into `invoice.with(..data)` and it compiled unchanged. JSON fails as-is in five places: `date`, `service-period` and `preceding-invoice-date` need a datetime; `tax` needs a ratio or a full 4-key dict; `auto` cannot be written (null≠auto, and the string "auto" is rejected). Numbers are also rejected in text fields: `invoice-nr: 42` panics, and `sender.vat-id: 123` crashes inside the theme. Two fields accept strings with a different meaning: `due-date: "2026-02-01"` is taken as payment-terms text (BT-20), not a due date (BT-9), and a string `order-date` is printed verbatim. TOML is the only Typst-native format that yields datetimes (verified). No string→date parser exists in the code; the only string coercer is theme.custom.from-data (theming/data.typ:14-38: "#hex", "10pt", "66%", "none", "auto"). It is a good precedent: it takes a decoded dict plus an `assets:` callback, because packages cannot open user paths. I verified that on 0.14.2 and 0.15.1; `path()` works only on 0.15. Party dicts are pass-through: normalize-party keeps every input key (country.typ:959-990). Custom fields (e.g. `x-wappen`) therefore reach ctx and are readable by info.get/dynamic and by theme parts, but they raise IP-KEY-01 warnings (or IP-KEY-02 errors for alias collisions like `mail`) in the e-invoice. The 28 ctx keys that are always set and the 6 set only when given are listed in raw_notes. My measurement confirms the 'ctx values cost time' comment: a 2500-leaf dict in ctx made the 50-line benchmark 48% slower and the 300-line one 76% slower; sealed in `metadata()` (as the theme already is) the cost was ≈0, and 20 small fields stayed within noise. `dynamic`/`info` already work as a draw-time data binding (ctx path lookup with fallbacks), but they cannot see through a sealed metadata value. Assessment: a purely additive mapping works. My prototype `invoice-args(data)` + `invoice.with(..skeleton).with(..invoice-args(json(..)))` turned JSON into a valid factur-x.xml on both compilers with zero changes to invoice(). Three gaps need additive extensions: a slot for top-level custom data (invoice() rejects unknown args, and `apply` does not reach theme parts), a namespace for custom party keys free of warnings, and a data path for the body (items, bank-details, payment-terms), which is not part of invoice() at all.

## Implications

- The data format can be mapped onto invoice() without touching its signature: a new exported pure function (e.g. `invoice-args(data)` / `from-data(data, assets:)`) converts a decoded dict to named args, and the skeleton applies it last via `invoice.with(..skeleton).with(..converted)`, so data wins. This follows the existing theme.custom.from-data pattern (decoded dict in, `assets:` callback for files).
- The API must take decoded data (dict/bytes), not a file path: packages cannot read user files on 0.14. The CLI interface is therefore a skeleton line like `json(sys.inputs.at("data", default: "sample.json"))` or `json(bytes(sys.inputs.payload))`. An optional package-read `--input invoice-pro-data=<inline json>` (like invoice-pro-validation) is possible, but arg-length limits apply.
- Required coercions in the data layer: ISO date strings to datetime (date, service-period as [a,b] or {start,end}, preceding-invoice-date, due-date, order-date, item dates), rate strings like "19%" to ratio, tax objects to tax.new(..) (filling missing keys like data/tax.typ normalize does), the "auto" sentinel to auto (absent key = default, null = none), the locale name ("de-de") to a locale function via dictionary(locale), identifier objects {scheme: gln|siret|leitweg|register|<ICD>} to id.\* constructors (which gives check-digit validation for free), and numbers in text fields to strings or a rejection.
- due-date needs an explicit discriminator in the format (date vs payment-terms text). Coercing every ISO string inside invoice() itself would change existing behaviour of str due-date/order-date, so the coercion belongs in the data layer.
- Top-level custom fields need one additive param (e.g. `custom:`/`data:`) that, like the conditional keys at invoice.typ:601-617, is inserted into ctx only when given. It must be SEALED in metadata (measured: +76% on 300 lines for a 2500-leaf payload unsealed, ~0 sealed). dynamic's path traversal (dynamic.typ:169-177) then needs an additive unwrap of metadata.
- Custom keys inside parties already reach ctx and theme parts, but they cause IP-KEY-01 warnings in e-invoice reports. An additive fix is a reserved print-only key (e.g. `custom: false`) in zugferd/model.typ party-keys, or steering users to the top-level custom slot.
- Field-value-dependent design (Wappen by PLZ) needs no new mechanism: theme.custom.part/wrap closures get ctx (ctx.sender.post-code, ctx.recipient.post-code, custom fields). This stays design-in-Typst as requested. Large lookup tables should be captured in theme closures, which are sealed, not put into ctx.
- Precedence problem if a `data:` param is added to invoice(): the defaults of date, sender, recipient, tax-mode, tax-exempt-small-biz, zugferd-errors and validation are not `auto`, so explicit and default values cannot be told apart. A rule of 'data wins when the key is present' avoids the ambiguity. A separate converter plus `.with` gets the same result with zero signature change.
- Party merging: `.with` replaces dicts shallowly. If the skeleton holds a static sender (letterhead) and data only overrides some fields, the converter or helper must deep-merge party dicts explicitly.
- Speed: work at the input boundary is negligible (a few ms against ~700 ms for weave at 50 lines). Hydration speed is therefore decided in the loom tree (item scope ≈ 330 ms per 100 calls), not by parsing data. invoice() already runs the minimum of 1 measure + 1 draw pass.
- Phase 2 groundwork: matchers in utils/types.typ (rendered by display-matcher) and the party-keys table in zugferd/model.typ:357-407 are machine-readable sources from which a JSON Schema could be generated. TOML maps 1:1 including dates, which makes it a good human-facing format; JSON needs the string coercions.
- The body (line-items, item, bundle, group, discount/surcharge, prepayment, bank-details, payment-terms, direct-debit/card-payment/paid, signature) is NOT part of invoice(). The unified format needs a body-side hydration path, either skeleton loops (verified to work for items with str/float prices) or a new data-driven component, using the same coercions.

## Risks

- Silent semantic change: a string due-date means payment-terms text (BT-20). A naive JSON mapping of "2026-02-01" prints it verbatim and states it as terms, not as a due date (BT-9). It also collides with `paid` (root.typ:237-247 panics).
- JSON numbers in party/text fields are not caught at the boundary: they crash deep in the theme (frame.typ:16/220) with unhelpful messages. The data layer must validate.
- Putting big custom payloads (lookup tables, raw source records) into ctx unsealed slows compiles by up to 76% (measured). This includes custom keys inside party dicts, which can never be sealed.
- Custom party keys trigger IP-KEY-01 warnings in e-invoice reports, and names that alias known keys (mail, tel, plz, zip, ort, land...) trigger IP-KEY-02 errors or hints that stop 'panic' mode, because the alias table in zugferd/keys.typ also matches German field names.
- Shallow `.with` override: data that provides `sender` replaces the skeleton's whole sender (verified loss of address), unless the converter deep-merges.
- Path-based loading is not portable: path() works only on Typst 0.15+. On 0.14 the user's file must call json()/toml(). Inline JSON via --input hits command-line length limits (inference: Windows ≈32K chars).
- `auto` cannot be expressed in JSON; null maps to none, which is invalid or different for subject, currency, references (none = no references) and tax (none = implicit zero tax). The format must treat 'absent' as default and define a sentinel.
- Rate ambiguity: a float 0.19 passes in tax dicts (rate float), but a bare float tax is rejected. A format allowing both 19 and 0.19 would be error-prone, so it should pick one (e.g. "19%" strings or decimal strings).
- Plain {scheme,id} identifier dicts from data skip check-digit validation; only id.\* constructors produce `problems`. A converter should route known schemes through the constructors.
- datetime.today() default makes batch output time-dependent unless the data provides `date` or the CLI sets --creation-timestamp / SOURCE_DATE_EPOCH.
- Measurements are wall-clock on a shared machine (±10%). The per-leaf cost of ctx is inferred from two points, and the locale-sealing benefit is an unverified inference.

## Open questions

- Precedence: should hydrated data override the skeleton's sample values (my prototype: data wins via .with order), and should party dicts deep-merge (static letterhead sender + data overrides) or be replaced?
- Where should top-level custom fields live: a new invoice(custom: ..)/data param (sealed, exposed as ctx.custom), a reserved `custom` key inside parties, or both? How do theme parts and dynamic/info read them (path unwrap of metadata)?
- Is `locale` per-invoice data (language of the recipient) or skeleton design? The same question applies to `references` (header composition is design; values are data) and `tax-mode`.
- Which number/rate convention: "19%" strings, decimal strings "0.19", or numbers? Should money values be strings (exact decimal) to avoid float rounding (coercion.to-decimal rounds floats to 15 digits)?
- Phase-1 CLI convention: does the package read a namespaced `--input invoice-pro-data=<json>` itself (precedent: invoice-pro-validation), or does the skeleton read the file and pass the dict? Should a `typst eval`/query output contract exist for phase 2?
- Should the coercion layer also relax invoice()'s own type checks (e.g. accept partial tax dicts, which data/tax.typ normalize already supports, or the strings "exempt"/"reverse-charge" that to-tax accepts) as a pure extension?
- How is the body hydrated: skeleton loops over data.items with a provided item-args() coercer, or a new data-driven line-items component? Does the speed goal require bypassing per-item loom motifs for data-driven items (out of my topic, but where the time goes)?
- Should rich text (bold, line breaks) be allowed from data? The project avoids eval deliberately (theming/data.typ:2), so it would need an opt-in markup field.
- Would sealing `locale` (215 leaves, unsealed in ctx) give a measurable general speedup (inference from the payload experiment; not tested)?

```
service-period strings   -> rejected    preceding-invoice-date str -> rejected
due-date str / order-date str -> OK (but text semantics)
zugferd "auto"           -> rejected    subject none / currency none -> rejected
references ("invoice-nr", ..) names -> rejected; ((A,1),(B,2)) and dict -> OK
notes ((text: x, foo: 1),) -> panic (strict note keys)
invoice-nr 42 / customer-nr 42 -> rejected
sender.vat-id 123        -> crash: expected content, found integer (theming/parts/frame.typ:16)
sender.city.post-code 10115 -> panic: must be a string such as "01067"
sender.country "de"      -> OK
invoice(wappen: "x")     -> error: unexpected argument: wappen
```

#### 2. Shape of party dictionaries

Sources: normalize-party (src/logic/country.typ:814-991), identifier keys (src/logic/party-inputs.typ:10-22), the authoritative key table `party-keys` (src/zugferd/model.typ:342-407; `true` = written into the e-invoice, `false` = print only), contact keys (model.typ:409-413), references/dynamic fallbacks (src/logic/references.typ, src/components/dynamic.typ), theme parts (src/theming/parts/frame.typ:219-242, src/theming/frame.typ:125-145).

**Address keys (all roles)** (`_address-keys`, model.typ:342-350):
| key | type | notes |
|---|---|---|
|name|str \| content \| array (lines)|joined with `\` (block) or ", " (inline)|
|address|str \| content \| array (lines)|mutually exclusive with `street` (panic)|
|street|alias of address||

|extra|dict \| array of (label, value)|print only; dict converted to pairs (root.typ:130,150); JSON object order kept|

**Seller = `sender`** (+ party-keys.seller): vat-id, tax-nr, id, global-id, legal-id, electronic-address (identifiers: text \| (scheme, id) dict \| id.\* typed dict (scheme, id, kind, problems)), trading-name, legal-info (text or array of lines), tax-representative (party dict: address keys + vat-id; normalized at invoice.typ:435-442), contact (dict name/phone/email, or a text = name), contact-name, phone, email (flat fallbacks; model.typ:208-234), register, management (print only: legal footer, frame.typ:228-242). Legacy: `bank: (iban, bic)` is read only by dynamic (dynamic.typ:132-163) and is not in party-keys (it would trigger IP-KEY-01).

**Buyer = `recipient`** (+ party-keys.buyer): vat-id, id, global-id, legal-id, electronic-address, trading-name, contact/contact-name/phone/email, buyer-reference \| leitweg-id (text or id.leitweg), order-nr, po-nr, contract-nr, delivery-note-nr, delivery-address (party dict; the top-level param wins, invoice.typ:444-452). Print-only: tax-nr, customer-nr, customer-id, order-date (day-checked at invoice.typ:279), project, quote-nr.

**Ship-to = `delivery-address`**: address keys + id, location-id, global-id. Without its own country it takes the buyer's country (invoice.typ:453-468).

**Payee**: name, id, global-id, legal-id (only `name` required).

**Identifier rules** (party-inputs.typ:38-77): a function value panics (uncalled id.siret). A dict without `id` panics, except electronic-address, which is then derived. Plain `{scheme, id}` dicts are accepted but **not** check-digit validated; only id.\* constructors carry `problems` (IP-ID-01). JSON `{scheme:"0088", id:"..."}` works as-is.

**Derived keys added by normalization** (never inputs): name-inline, address-inline, city-inline, address-lines, country (resolved dict incl. closures parse-city, format-address, format-inline), country-explicit, city-name, post-code, state (model.typ:437-447). `post-code` is what a PLZ-dependent Wappen reads.

**Unknown keys**: kept in ctx (country.typ:959-960 starts from `party`). With zugferd they are reported as IP-KEY-01 warnings, or IP-KEY-02 errors when they look like an e-invoice key (alias table zugferd/keys.typ:11-112 includes German names: plz/zip → city hint, mail → email, tel → phone, ort → city, land → country, steuernummer → tax-nr, ust-id → vat-id ...). Verified: `x-wappen` → IP-KEY-01, `mail` → IP-KEY-02.

#### 3. How inputs flow into the loom context

1. invoice() validates, resolves the locale (`locale(base-language, base-region)`, + with-currency), resolves the document type, merges deprecated tax-nr, normalizes sender/recipient/tax-representative/delivery-address, resolves the theme with env (kind, lang, sender region, e-invoice) and checks it, computes subject = (subject, invoice-nr).join(" ") and document-tax, builds default references (invoice.typ:491-543), and computes up-front issues (check-data "input").
2. `inputs` dict (invoice.typ:563-597), **always present (28)**: theme (sealed: `seal(eval-theme)` = metadata(theme)), validation (level, issues), locale (unsealed, 215 leaves), format, sender, recipient, delivery-address, payee, invoice-date, subject, subject-text, references, invoice-nr, customer-nr, order-nr, order-date, project, contract-nr, quote-nr, delivery-note-nr, preceding-invoice-nr, due-date, payment-reference, tax, tax-mode, tax-exempt-small-biz, zugferd, zugferd-errors.
3. **Inserted only if given (6)** (invoice.typ:598-617, condition `value not in (none, auto, ())`): currency, service-period, title (only computed if zugferd != none), document-type (only if not auto; resolved dict), preceding-invoice-date, notes (normalized list). Comment: _"Document data most invoices leave out joins the context only if it is given: the context reaches every component and call, and each value it carries costs time on long invoices. It is read with a default."_ Readers use `ctx.at(key, default: ..)`, e.g. references.typ:189, 441.
4. weave(max-passes: 2, inputs, injector, root(body)) (invoice.typ:620-627) → loom runtime.typ:64 `base-ctx = empty-context + inputs`. measure-limit = 1, so **1 measure pass + 1 draw pass**; the convergence check (`i > 0`, runtime.typ:86) never runs. injector: `ctx + (global: payload.first().signal)`, so root's measured public (total, formated-total, bank, payment-means) becomes ctx.global in draw.
5. root scope (root.typ:110-188) `ensure`s defaults for sender/recipient keys (name, address, city, \*-inline, country "#sender.country" placeholder, city-name, post-code, state, tax-nr, vat-id, address-lines, extra → pairs), invoice-date, subject, references, invoice-nr, validation, locale.lang/meta.region/format.date, zugferd(-errors), global totals.
6. root draw (root.typ:305-606) evaluates references builders against the ctx (items, payment-terms, bank), runs the measured validation, builds and attaches the ZUGFeRD XML, sets document metadata, and calls render-frame(ctx, body). The theme parts receive this root ctx (unsealed), so **anything in inputs is visible to theme parts**; keys injected with `apply` in the body are not.
7. Dead fallbacks: references/dynamic also read top-level ctx keys that invoice() never inserts (po-nr, project-nr, offer-nr, original-invoice-nr, contact-person, clerk, buyer-reference). Only `apply(..)` can provide them, and only inside the body (references.typ:288, 334, 365, 424, 511; dynamic.typ:85, 122).

**Why it matters (measured)**: copies of the repo with one extra inputs key (exp/invoice-entry/r-\*), benchmark from tools/perf/gen_bench.py (kind b, plain):

| variant                         | b-50 median           | b-300 median          |
| ------------------------------- | --------------------- | --------------------- |
| base                            | 1398 ms (run 2: 1189) | 5681 ms (run 2: 5800) |
| +2500-leaf dict, plain          | 2070 ms (+48%)        | 9990 ms (+76%)        |
| +same dict sealed in metadata() | 1292 ms (≈0)          | 5677 ms (≈0)          |
| +20 short string fields, plain  | 1258 ms (noise)       | 5788 ms (noise)       |

So the cost scales with payload leaves × motif calls (≈1.7 ms per leaf at 300 lines). Small scalar keys are free; big payloads must be sealed like the theme (theming/access.typ:1-11).

Trace of b-50-plain (`typst compile --timings`, tools/perf/trace_agg.py): total 1279 ms; invoice() 735 ms, of which weave 679 ms; item scope (item.typ:200) 330 ms / 100 calls; input boundary negligible (resolve-party-country 2.2 ms, check-identifiers 0.3 ms, check-data 0.5 ms, normalize-notes/resolve-document-type <0.1 ms). A data-coercion layer at the input boundary is effectively free.

#### 5. dynamic / info: the existing data-binding mechanism

- `dynamic(..path, default: none, format: auto)` (components/dynamic.typ:310-327) is a loom **content-motif with draw only**: `content-motif(draw: _draw.with(path, default, format), body: none)`. At draw time `_draw` (25-295) resolves:
  - a closure `ctx => value` (most flexible),
  - single-key shortcuts with fallbacks: invoice-nr, invoice-date/date, due-date (computed from payment-terms days/date), customer-nr/customer-id, order-nr/po-nr, order-date, project, contract-nr, quote-nr, delivery-note-nr, preceding-invoice-nr, payment-reference (resolved like bank-details), buyer-reference/leitweg-id, subject, tax-nr, vat-id, iban, bic, else `ctx.at(key)`,
  - dotted or multi-arg paths walked through **dictionaries only** (169-177), with special fallbacks for locale region/lang, bank iban/bic, total gross/net (formatted).
  - Formatting: datetimes via locale.format.date, arrays joined with ", ", dicts with `id` print `.id`, else `[#val]`; a custom `format:` fn wins.
- `info` (public/info.typ) predefines accessors: info.invoice-nr, date, due-date, …, info.sender.(name, trading-name, legal-id, legal-info, tax-nr, vat-id, address, city, country, email, phone), info.recipient.(…), info.total.(gross, net, due, prepaid); `info.get` = `dynamic`.
- So the skeleton can already contain bound placeholders (`#info.recipient.name`, `#info.get("recipient", "x-kundenart")`, `#dynamic(ctx => ..)`) that fill from ctx at draw time. Verified: custom party key printed via info.get. **Limit**: a sealed metadata value is not traversed (verified: path lookup empty, closure that unwraps `.value` works). Exposing sealed custom data would need an additive unwrap in `_draw`.
- Related: `apply(..args, body)` (loom-wrapper.typ:18-22, exported) merges named args into ctx for a body subtree. Verified it does not reach theme parts (logo saw nothing).
- PLZ-dependent design already works in Typst: `theme.classic.with(theme.custom.part("logo", (ctx, view) => wappen(ctx.sender.post-code)))` rendered "WAPPEN-BAYERN" for "80331 München" (exp/invoice-entry/wappen.typ).

#### 6. Assessment: can data be mapped purely ADDITIVELY?

**Yes for everything invoice() takes, with zero signature change.** Prototype in exp/invoice-entry/hydrate-proto.typ (≈50 lines, not production):

```typst
#show: invoice.with(            // skeleton: design + sample data
  theme: theme.classic.with(theme.custom.part("logo", (ctx, view) => wappen(ctx.sender.post-code))),
  sender: (..sample..), recipient: (..sample..), invoice-nr: "SAMPLE",
).with(..invoice-args(json(sys.inputs.at("data", default: "data2.json"))))   // hydration: data wins
```

`invoice-args` coerces ISO dates (date, due-date, order-date, preceding-invoice-date, service-period as [a,b] or {start,end}), "7%" → ratio, tax objects → tax.new(..), "auto" → auto, locale "en-de" → dictionary(locale).at(..), identifier `{scheme:"gln", id}` → id.gln(..), and drops `custom` (no slot). Result on 0.14.2 and 0.15.1: correct rendering plus a valid factur-x.xml (GlobalID schemeID 0088, DueDateDateTime 20260315, BG-14 20260201–20260228).

**Gaps that need additive extensions**:

1. **Top-level custom data**: invoice() rejects unknown args, and `apply` does not reach theme parts → add one new param (e.g. `custom: none`). Insert it into ctx only when given (pattern of invoice.typ:601-617), sealed in metadata (perf), plus a metadata unwrap in dynamic's path traversal. Additive.
2. **Custom party keys**: work today, but produce IP-KEY-01 warnings or IP-KEY-02 errors. Add a reserved print-only key (e.g. `custom: false` in party-keys / `_address-keys`) or route custom data to (1). Additive.
3. **Body data** (items, bank-details, payment-terms, payment means, prepayment, signature): not reachable through invoice(). Skeleton loops work (`#for it in data.items { item(it.remove("name"), ..it) }`, verified with str/float prices), but item date/tax strings need the same coercion. Needs a coercer for item args or a data-driven component. Additive.
4. A `data:` param on invoice() itself is possible additively, but: (a) defaults that are not auto make explicit vs default undecidable, so "data wins when present" is the only clean rule; (b) parties need deep-merge semantics; (c) coercing ISO strings inside existing params would CHANGE the meaning of str due-date/order-date. That is a breaking semantic change and is better avoided.
5. Packages cannot read user paths on 0.14. The API takes a decoded dict (or JSON text via sys.inputs). The skeleton does the `json()`/`toml()` call, or the package decodes `--input invoice-pro-data=<inline json>`.
