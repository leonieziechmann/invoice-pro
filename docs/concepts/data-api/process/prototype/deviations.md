## Deviations from SYNTHESIS.md (and why)

1. **"Direct child of `line-items`"** for the marker means: no `group`/`bundle` between `line-items` and the marker; an `apply(..)` around it is transparent. Needed for the P1 fixture "apply around the slot" (the engine judge's `wrap=1` case puts the marker inside `apply`). The check reads the loom path in the marker's measure (`apply` adds no path segment).
2. **"At most one marker"** is asserted per `line-items` by the implicit slot (it counts the marker frames of its children); together with root's existing "only one `line-items`" assertion this is at most one per invoice. The marker talks to the slot through a frame of its own kind (`invoice-data-items`), which the slot always removes. Root's measure does not see markers.
3. **Item modifiers have no `tax`** (new descriptor object `item-modifier`): `item.typ` panics when an item's modifier pins another VAT category, so the format leaves the key out at item level (unknown-key issue). §3.6 lists `tax` for modifiers at every level.
4. **Additional decoder-only rules** (crash-freedom, found by the fuzz corpora or by reading the guards): ≤ 28 significant digits per decimal (the spec pattern admits 30, which `decimal()` rejects with a hard error), `|price × quantity ÷ base-quantity| < 10^18`, `base-quantity` > 0 and ≥ 0.0001 after rounding to 4 decimals (calc-item guard; the schema's `decimal-positive` is a plain pattern, see 22), `note`/`origin` dropped from items of a bundle (C's rule), a bundle without a valid item is dropped, `null` as an array element is an issue; added in fixer round 1: **a text has at most 10 000 characters** (code points; a longer unbroken word exceeds the 32 767-byte PDF string limit of PDF/A, verified: 30 000/33 000-character names, notes, terms text and unknown keys aborted under `--pdf-standard a-3b`), **a date's year is 1–9899** (Typst's time crate aborts with a Rust panic, exit 101, past 9999-12-31, and a due date is date + payment days), **groups/bundles deeper than 8 are rejected before their rows are decoded** (the recursion reached Typst's call-depth limit at depth ≥ 24). They are not expressible in the JSON Schema without breaking the code generators (a `maxLength` on every string makes typify wrap every string in a newtype) and appear as `decoder-only` conformance fixtures (`text-10001`, `date-year-9999`, `depth-30`).
5. **Percent pattern** is the spec's `^[0-9]{1,3}(\.[0-9]{1,6})?%$` in both decoder and schema (D used `-?[0-9]{1,6}(\.[0-9]{1,8})?`).
6. **Tax objects** become `tax.new(rate, category, label: <the constructor's label>, grounds, code)` (C's mapping), equal to the `tax.*` constructors' dictionaries; this also carries `code` and `label` for every category. `"19%"` stays a ratio resolved by the region's `infer-tax` (as §3.2 says; D converted it to `tax.vat`).
7. **Region pass** runs in `hydrate()` with the locale's region (and in `decode`/`check` with `region:`), and leaves the offending `tax` value out (not the row), following §8.3 ("an invalid value is left out").
8. **Small business vs `tax` across layers** (not in the spec): the data's `tax-exempt-small-biz: true` drops the skeleton's `tax`; the data's `tax` under the skeleton's exemption is an issue `schema/tax` (invoice() would panic). Within the data, a new object rule `excludes-if-true` (descriptor + JSON Schema) makes `tax` + `tax-exempt-small-biz: true` an issue.
9. **Classes of the signature test** are `design | document | issuer | data | body` (`invoice-params` in schema.typ); `custom` is classified `document` (its role per Q3) rather than a class of its own.
10. **`vat-rates` needs a base entry** (`normalize.vat-rates: none` in region/base.typ): the locale factory rejects region keys the base does not declare. `infer-tax` is not rewritten on top of the list; a unit test pins that every listed rate resolves.
11. **The implicit slot lives in `line-items.typ`** and imports `contract/rows.typ` only when hydrated (so benchmark invoices without data never load it); `rows.typ` holds C's engine and the marker.
12. **Result module**: the record builder (`contract/result.typ`) loads no descriptor; its shape is declared in `contract/result-schema.typ`, loaded only by `schema(kind: "result")`. D's `--input invoice-pro-result=attach` is dropped (Q6 follow-up). It reads the package version from `../../typst.toml` (relative) instead of `/typst.toml`, so the prototype also works with a root outside the package. Root reads `--input invoice-pro-result` from `sys.inputs` directly (not injectable).
13. **`load()` without a data input returns `none` without loading any contract module** (cheap preview); `decode()` never consults `sys.inputs`, so a `decode(..)` record plus a CLI data input panics as two sources.
14. **Integration tests**: the repo has 66 `tests/integration/**/test.typ` (60 top-level + 6 nested; 59 compile to PDFs, 7 are expected-panic tests), not 53. `proto/regress/integration.sh` now globs recursively (round 1; it compared the 60 top-level ones before).
15. **Template md5**: compared pristine vs prototype under the same layout (`template/_tpl.typ` with the import rewritten, `--root <tree>`). The synthesis' `ba5d9a49b5de` (0.15.1) / `c7e98da669bc` (0.14.2) are the template compiled **with `--pdf-standard a-3b`** (as in `exp/synth`); `881821b7318c` / `8a1c8b464422` are the same template without `--pdf-standard`. The prototype reproduces both pairs exactly (equal to pristine). (Corrected in round 1: the earlier text blamed "another file location".)
16. **Edge fixtures**: `#payment-terms(days: 14)` / `#payment(terms: (days: 14))` appended to the engine judge's edge twins, so they are valid e-invoices with `zf=auto` (IP-PAY-06 otherwise stopped pristine too). The fuzz skeleton got `#payment(terms: (days: 14))` for the same reason.
17. **Conformance fixtures** are regenerated for the trimmed format (72): D's extension-based cases (declared custom fields, Q7) are dropped or became valid (open bags); new cases for `kind: null`, units by pattern, `terms.text`, small business, item modifiers, `decoder-only` rules, and three default model dumps (two null-filled from the schema, one real pydantic `model_dump()`). D's literal 51 fixtures are also checked for schema/decoder agreement (labels aside).
18. **Perf gate entry (L18)**: only `LAZY_MODULES` is extended in `tools/perf/gate.py`; the "hydrated 300 rows ≤ 0.6×" gate is `proto/bench/p9.py`, not a gate.py entry.
19. **L16 locale strings and the "Daten / Data" chip are not implemented** (English messages only; issues use `key: schema-*` so a locale could translate them).
20. **Generated / copied fixtures are not typstyle-formatted** (`proto/eq/hand/*`, generated by gen.py; the engine judge's `edge-hand.typ`, `e2-hand.typ`, `common.typ`, `e2-common.typ` kept as copied). Every `.typ` file changed or added in the repo is typstyle-0.15.1-clean.

### Fixer round 1 (verifier findings)

21. **Cross-field rules are `dependentSchemas` in the JSON Schema** (exactly-one, at-most-one, exclusive, excludes-if-true, the new only-with and nonzero-if, a filled line of required `lines`). D's `oneOf`/`not` over property subschemas made json-schema-to-typescript type `price`/`total` as `{[k: string]: unknown}` (every valid item row failed `tsc`) and opened Root/Buyer/Payment/Terms/Item to typos, and made typify degrade 11 fields to `()` (949/952 valid documents failed to deserialize); `if`/`then` makes typify panic. `dependentSchemas` is enforced by every validator (python-jsonschema, ajv) and ignored by the three generators (verified on a minimal schema and on the full one). The lower bound of exactly-one (price or total) is a `not` hung on the object's required key `name`. Result: `tsc --strict` 0 errors on the §3.10/maximal documents, all row shapes accepted, typos rejected at every level; typify types deserialize every schema-valid document and re-serialize it unchanged (only the default `kind: "item"` is filled in). The spec (§10.1) names no encoding; the conformance fixtures keep the verdicts.
22. **`decimal-positive` is a plain unsigned pattern** (no `allOf`/`not`, which made `base-quantity` untypable); > 0 (indeed ≥ 0.0001) is decoder-only (the D fixture `zero-base-quantity` is accepted as decoder-only by `agree.py`). Percentages that must be > 0 (tax `"19%"`) or in (0, 100) (cash discount) use exact positive patterns instead (`percent-positive`, `percent-0-100`; a 0% or 100% discount crashed `cash-discount`).
23. _(Narrowed by 36 in round 2: for `""`, the schema follows §3.3 for texts only.)_ **Schema follows §3.3 for `""` and `null`**: an optional patterned text (currency, country, origin, unit/tax codes, debtor IBAN, document type) accepts `""` (pattern `^$|…`), which the decoder reads as absent; map values (`extra`) accept `null`. Integral JSON numbers (`14.0`) are integers for the decoder too (as for JSON Schema; |n| < 2^53). Required texts carry `minLength: 1` + `pattern: "^\\s*\\S"` and required `lines` need a filled line, as the decoder now asks (§3.2 "a required text must not be empty": blank lines or spaces gave a final e-invoice with BT-44 `,`).
24. **Document types are exactly those `invoice()` accepts**: the named types, `self-billed-credit-note` (mapped to UNTDID 261, which `invoice()` knows as a self-billed credit note; it has no name there) and the UNTDID 1001 codes of `logic/document-type.typ` (this includes the two-digit codes 71–84 the spec's `[0-9]{3}` excluded, and excludes the 3-digit codes `invoice()` panics on, e.g. 001, 999).
25. **Payment rules**: (a) the details of one method with another `method` (`method: "transfer"` + `card`) are a data issue and left out (new descriptor rule `only-with`; §3.7 does not cover it, §4.5 "never dropped silently"); (b) **hydrated only**, `payment(..)` turns what the components stop on into data issues: a credit note / self-billed invoice drops the cash discount (data's or skeleton's) and a direct debit / card (the components' guards still panic for Typst authors and for `payment(..)` without data, so its md5 stays equal to the hand-written components); (c) **hydrated only**, a transfer with no account is a data issue when the data chose it (`payment.method`) or it replaced the skeleton's own method (a sample direct debit/card dropped); a skeleton's own transfer without a bank stays as written (= the hand-written components, keeps P1). `payment.terms.days` ≤ 36 500 (schema `maximum`). A `payment.bank` without IBAN stays a partial object (§8.3 lists `bank` as partial), so it is reported by the decoder and by `bank-details` (two issues, by design).
26. **Near-miss input keys panic** (R7/L7): any `--input` key whose normalized form (lower case, without `-`, `_`, `.`) starts with `invoiceprodata` but is not one of the two data keys (e.g. `invoice-pro-data-fil`, `INVOICE-PRO-DATA-FILE`, `invoice_pro_data_file`). Decision: other `invoice-pro-*` keys (e.g. `invoice-pro-json`) are **not** caught: L7 justifies the panic for the reserved `invoice-pro-data*` prefix only, and a skeleton may read keys of its own with the same package prefix; a broader rule would change non-hydrated invoices.
27. _(Superseded by 43 in round 2.)_ **A marker nested in a marker's sample is detected only without data** (decision, not fixed): hydrated, the outer marker's sample is never traversed (that is the point of the closure-held marker), and the output is still correct (the rows are placed once by the outer marker; the inner marker is part of the dropped sample). The preview, which every skeleton author runs, panics with "at most one".
28. **Unallocatable document modifier (hydrated only)**: an absolute modifier without `tax` whose items have no VAT group, or whose ≥ 2 groups add up to 0, stopped `modifier-applicator` (known gap before). Hydrated, it is left out with a data issue `schema/modifiers` (issue built in the lazy `contract/hydrate.typ`, carried as `item-data.data-issues` to root's hydrated-only branch); written in Typst it still panics.
29. **Bugfix on the shared path (S8-style, would be its own PR)**: `theming/parts/frame.typ` `_one-line` crashed (`none.trim`) when not even one cluster of a long text fits the header line (an invoice number of ≈ 400+ characters made of words; pristine hand-written invoices abort identically). It now prints the ellipsis. Output of every document that compiled before is unchanged.
30. **`payment` is exported through a facade** (`src/public/payment.typ`: the public signature and docs; the body imports `components/payment.typ` when an invoice uses it), so the root import does not parse the implementation (P9).
31. **Result record**: totals follow `payment.paid` as the e-invoice does (BT-113 = gross, BT-115 = 0); `taxes[].code` is the BT-121 the XML states (none for S/Z/L/M or for items with different codes, the category default `VATEX-EU-AE/IC/G/O`); negative amounts are written with `-` (Typst's `str()` writes U+2212, which broke the result's own decimal pattern); money values have two decimals (`0.00`).
32. **Behaviour change on the non-hydrated path, listed (L13 ⚠)**: `custom` is a known print-only party key (`zugferd/model.typ`), so a hand-written 0.6.0 invoice that passes a party `custom` key loses the IP-KEY-01 warning in the e-invoice report (only visible with `zugferd-errors: "report"`; default PDFs identical, verified by the equivalence verifier). And (L5 ⚠) `import *` now also binds `payment` and `invoice-data`, shadowing a user binding of that name defined before the import.
33. **Signature test** (`tools/contract/signature.py`): also fails on a class or role that is none of `param-classes` (a typo silently dropped the skeleton's theme or a data key) and when `data`/`body` lose their structural class; `hydrate()` panics on an unknown class instead of skipping it. It runs on 0.14 through `typst query` of a stub (0.14 has no `eval`).
34. **Decoder hot path** (P9): fields carry a precomputed dispatch class (`fast`), objects precomputed rule flags; union objects (item-id, tax objects), arrays of objects (modifiers) and **row arrays are decoded inline**, without a memoized call of their own: each memoized call level around a row multiplied its cost (one group level tripled it). Verdicts and issues are unchanged (108/108 + 51/51 fixtures).
35. **Blank required values on the hand-written path stay as they are**: `check-data` (pre-existing, non-hydrated) still accepts `name: ("", "")`; only the data path rejects it. A `check-data` bugfix would change non-hydrated reports (S8 candidate).

### Fixer round 2 (verifier findings)

36. **`""` ≡ absent for every optional key; the schema allows it for texts only** (P1.blank-optional-absent). §3.3 says "an optional `""` is absent" in general, the §3.2 table says it in the `text` row. The decoder now reads `""` as absent for an optional key of any type (date, period, decimal, percent, amount, tax, unit, enum, integer, boolean, object, and `kind` → the default case: empty cells of spreadsheets and forms), a required `""` is "must not be empty" (before: texts only). The JSON Schema accepts `""` for texts only (as before, `^$|…` patterns): a `""` alternative for a date, decimal or enum would turn their generated types into unions (typify maps `format: date` to `NaiveDate`, enums to Rust enums). So `""` for a typed key is a fourth leniency of the reader (conformance fixtures `blank-*`, `lenient`), beside `null`, JSON numbers and TOML dates (§3.1.6 lists three). In the cross-field rules the schema counts `""` as absent (`dependentSchemas` with `enum: [null, ""]`), so `terms.text: ""` next to `days` is valid for both.
37. **PDF/A string limits** (P4.v3-new-files, P4.H10). `invoice-nr`, `subject` and a party's `name` (all its lines, joined by a space as the PDF metadata takes them) have at most 4000 characters (`schema.max-meta`): they become the PDF title, description and author, which PDF/A writes in UTF-16 (4 bytes per character beyond the BMP) with at most 32 767 bytes, and the title adds the document's name to the number. Schema: `maxLength: 4000` on the strings; the total of a name's lines is decoder-only. Strings inside the `custom` bags have at most 10 000 characters (`max-text`, decoder-only; an iterative scan, bags may nest deeper than Typst's call depth). Noncharacters U+nFFFE/U+nFFFF in any text or custom string are a data issue (no font has a glyph; PDF/A stops: verified for U+FFFE, U+FFFF, U+2FFFE, U+10FFFF). Not covered, pre-existing and the same for hand-written invoices: a character that no installed font covers stops PDF/A (found U+A646, U+A74C, … here; CJK/Thai with `--ignore-system-fonts`) — that depends on the fonts of the skeleton and the machine, not on the data.
38. **A cash discount has at most 2 decimals** (P4.valid-docs-compile-sweep (2)): schema `percent-0-100` and decoder (`t.percent(digits: 2)`); `cash-discount.typ` stops on more (the e-invoice states 2). Every value 0.01 %–99.99 % passes the component's guard (checked exhaustively). Its `days` have at most 36 500, as `terms.days` (the v3 corpus' `skonto_days_36501` and `_1e15` were accepted; a period of 10^15 days is a typo, not a crash).
39. **`sender.management` as lines** (P4.valid-docs-compile-sweep (1), P5.round1-crash-repros): `theming/parts/frame.typ` `registration` printed `s.management` with `rows.push`, so an array stopped with "cannot join content with array" — hand-written invoices too (pristine). It now prints an array one entry per line, as §3.2 types it (`lines`). Bugfix on the shared path (S8-style, its own PR); every document that compiled before is unchanged (P2).
40. **`check()` never stops on data that is no object** (P4.check-never-panics): `none`, arrays, numbers, booleans, content and text that is no JSON object give `valid: false` with the issue `schema` ("invoice data must be a JSON object, found …"). JSON text that does not parse still stops as `json(..)` does (Typst has no try). Documented: `check()` is what the decoder checks; a hydrated invoice can report more (skeleton rules, e-invoice rules, credit note + Skonto, coverage).
41. **`payment(..)`: paid by transfer without an account** (P6.paid-transfer-without-account): the data's `paid.method: "transfer"` without any account is a data issue `schema/payment/bank` (CII-SR-470 stopped the compilation); a `paid` from the data counts as the data's choice of method. Decision (P6.bank-with-other-method): a data `payment.bank` with another method (card, direct debit, paid by cash or card) is left out **without** an issue: §4.4's emission rule writes the account "for a transfer and for an invoice paid by transfer only: an invoice states one payment means" (CII-SR-467), and `bank` is an issuer key (standing sender data, it replaces the skeleton's account whole), so it behaves exactly as the skeleton's own account; §4.5's "never dropped silently" is about sections without a binding point (coverage issues).
42. **`payment-terms(discount: ..)` in a skeleton + credit-note data** (P4.H7): hydrated, the skeleton's cash discount on a credit note or self-billed invoice that the data's `document-type` made is left out with the data issue `schema/document-type` (it addresses the data author, names the fix `payment(terms: ..)`); the component's panic stays for Typst authors and the preview. `payment-terms` remains no binding point of the data's `payment.terms` (the coverage issue `schema/payment` says so).
43. **A marker nested in a marker's sample panics with data too** (P3.nested-marker; supersedes 27): the marker's motif body carries a sign (`metadata("invoice-data-items")`), and hydrated, the marker scans its sample for it (an iterative walk of the content, the sample is still not woven) and panics "at most one … found one inside another".
44. **Result record** (P8): `taxes[].rate` is rounded to the 6 decimals of the format's percentages (a ratio is a float: rates of 100 % and more came back as `999.9999989999999%`); `invoice-nr` and `recipient` are written as the e-invoice states BT-1/BT-44 (whitespace collapsed and trimmed, invisible format characters removed, the lines of a name joined by ", "). `recipient` stays the data's recipient (the addressee); its schema description now says so: BT-44, or BT-27 on a self-billed document, whose XML writes the recipient as seller.
45. **Whitespace in the JSON Schema** (P5.targeted2): required texts use the explicit Unicode White_Space class (`[\t-\r \u0085\u00A0\u1680\u2000-\u200A\u2028\u2029\u202F\u205F\u3000]`, what the decoder's `str.trim` removes) instead of `\s`/`\S`, which differ between python `re` (U+001C–U+001F), ECMAScript (U+FEFF, not U+0085) and Rust.
46. **Integral JSON numbers for integers (`14.0`) stay valid** (P5.rust-typify-codegen; JSON Schema semantics, deviation 23): a known code-generator limit — serde's `i64` (typify) rejects `14.0`, pydantic and TypeScript accept it. Producers write integers without a fraction (all generated models do). The U+FEFF failures of that check are fixed by 45.
47. **Signature test** (P10.mutations-extended): `tools/contract/signature.py` reads the parameter list with a scanner that knows comments, strings and brackets: any identifier is a parameter (`water_mark`, `waterMark`, `qr2`), several on one line and multi-line defaults are read, an argument sink (`..extra`) fails; the same for the `hydrate(..)` call. Wired into `.github/workflows/tests.yaml` (a step after the docs examples; not run here: no nix).
48. **Decoder hot path, round 2** (P9.decoder-per-row-r-t): a call of a package function costs ≈ 25 000 instructions (it is memoized), so the hot path makes fewer: the region pass first scans the rows without calls (and leaves the values as they are when every rate is the region's); dates and objects of plain optional texts (`item-id`, declared `simple` in the descriptor) are read inline; a required text's limit is precomputed (`field.limit`); the amount-range guard of an item compares decimals before it converts them; the list of given keys became dictionary lookups; the case types of rows are prebuilt. Instructions per row (valgrind, deterministic, 0.14.2): t −20 %, r −12 % against the round-2 start; `check()` reports byte-identical on 7 corpora (3154 mutations, 1024 valid documents, …) and the 133 conformance fixtures. (Tried and dropped: passing rows by path into a sealed document, +2 %.)
49. **Root import delta** (P9.root-import-delta; known gap, decision): the facade bodies moved into the lazy `contract/api.typ`, the unallocatable-modifier test into `contract/hydrate.typ`. The root import parses +17.1 KiB (+6.1 KiB outside comment lines; round 1: +18.9 / +7.8). Measured here: ≈ 0.08–0.13 ms per KiB of code (parse + top-level evaluation) and ≈ 0.01 ms per KiB of comment lines, so ≈ 0.6–0.9 ms; trace spans of the whole root import (≈ 150 ms) cannot resolve the difference (paired median +0.6 ms ± several ms). The 0.2 ms budget comes from A/C's facade-only evaluation timings, which leave out parsing and any hook in `invoice()`. What remains is the documented API the design asks for: the two documented `invoice()` parameters and the re-entry hook (`invoice.typ` +1.9 KiB code), the items slot (`line-items.typ` +0.9 KiB), root's result and coverage hooks (+0.7 KiB), the two documented facades (+1.4 KiB code), the regions' VAT rates. Reaching 0.2 ms would need an undocumented `..args` wrapper around `invoice()` (it loses the signature, the docs and the LSP hints) or facades without docs; not done.
